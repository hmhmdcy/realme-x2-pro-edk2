# Optional EUD CSR save/disable/restore stage

This offline same-Image candidate adds `eud_com_csr_begin(cookie,result)` and `eud_com_csr_restore(cookie,result)` to frozen EUD software-window R2. No consumer, exported symbol, UAPI or default activation is added. `r2-to-csr.patch` applies to exact R2 source SHA `1479c3cf0be0b4d62a2b66486b3be5819f28da3d380c95ed76c2a1e6966db3af` and header SHA `8003aa9619d2f9d1a15d4ff97460b8f106dc54defc841f31670e98d48e2d8c46`. R2's final producer joins and all unrelated driver bodies remain unchanged.

## Returning CSR operation

The existing Image-linked COM probe writes CSR_EUD_EN=1; its reboot tail writes 0 and reads it back. Those operations establish the source-level 0/1 convention reused here. The new returning API never invokes that tail or `kernel_restart`. It saves the actual runtime register, never probe history, and only accepts whole values exactly 0 or 1. Other values produce EOPNOTSUPP after one read, with no write or hardware owner. This deliberately makes no claim about undocumented register states.

The window mutex serializes CSR operations against software end, remove, probe and PM. Before MMIO, the API requires an exact nonzero completed quiet cookie and rejects PM, stopping, accepted F1/reboot and its own RX/TX work context. Entry after cancellation is rejected. The existing UART gate prevents a new reboot decision while quiet; there is no wait, PM call or inter-component callback under the UART lock. Each API returns without any EUD lock held.

For supported entry, the actual prior 0/1 is saved and hardware ownership is established before a possible write. Old 1 is written to 0 and compared exactly by readback; old 0 is borrowed without an unnecessary entry write. Failed readback retains the owner and software quiet. A repeated supported begin is EALREADY with no MMIO, including after successful restoration; a fresh software quiet session is required for another borrow.

Restore is explicit and is allowed after cancel. It reads the current register; if it already equals the saved prior value, no write is needed. Otherwise it writes only that saved 0/1 and reads back exactly. Failure retains ownership and quiet; successful comparison alone releases the hardware owner. `quiet_end` returns EBUSY and never enables IRQ or queues producers while that owner remains. Cancel never restores CSR or resumes producers by itself.

`eud_com_csr_result.error` describes this API call. `enter_error` and `restore_error` retain their first actual register-stage errors independently; a successful explicit restore retry has `error=0,restored=true` while preserving earlier failure history. Guard/usage errors are returned in `error`, without modifying the saved CSR receipt. `saved_valid/saved_value`, `readback_valid/readback`, `csr_touched` and `hardware_owned` describe this borrow. The software result also exposes CSR write history and outstanding hardware ownership.

Remove is terminal, not a restore opportunity. Under the same mutex it saves a terminal CSR receipt, tears down the endpoint using R2's final joins and does not access CSR to invent recovery. A matching CSR restore then returns ENODEV with `removed=true,restored=false`; an outstanding `hardware_owned` in that terminal receipt records the interrupted borrow and grants no usable MMIO lifetime. `disabled_verified` refers only to the last register observation. Wrong cookies do not receive another session's saved state. Exact software `end(old_cookie)` only acknowledges removal and releases the reprobe interlock, still returning ENODEV with `restored=false`; it discards the internal tombstone and does not repair hardware. The outer owner must retain the terminal receipt before acknowledgment. A later binding has a new cookie; the old cookie cannot control it.

## Scope and future owner

CSR=0 readback proves only the observed enable register is disabled. It does not prove hub removal, DP/DM electrical route, high-Z, APSD completion, host enumeration or permission for 500mA. No AHB2PHY access is added: 0x11 configures bridge wait states and is not treated as a route/mux. No FIFO, descriptor, OTP/strap, PHY, PD, power-supply or charging-budget operation is added.

The COM binding has no generic power/clock/PHY reference that can truthfully guarantee powered MMIO. The future owner must maintain the independently established active/powered lifetime and exclusive hardware phase, use this API only in process context outside EUD callbacks, cancel/join before endpoint teardown, and decide the audited cross-component order. It must restore this CSR stage before software `quiet_end`. EUD, DWC and PHY API calls must be sequential with no component lock held across another component's call. This candidate neither resumes hardware to obtain access nor catches an architectural abort caused by an invalid/unpowered mapping. Cross-component routing and the eventual physical recovery sequence still require separate review and controlled hardware validation.
