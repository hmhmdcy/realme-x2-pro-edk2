# DWC resume error propagation: changes required before deployment

This is a limited independent review of `apsd-dwc-resume-error-candidate/core.c` SHA `cdff700a415cfa0de231dded3b00b18a31aae23de19dd4a894c894517bc06e2d`. The earlier [USB resume audit](../../charging-oem-audit-20261023/usb-resume-errors/README.md) already identified the swallowed return value and explicitly left resource/PM rollback open. Its 126 assertions and root's new eight-group/gate receipt are reused, not rerun. This review adds caller/resource evidence for that existing gap; it does not identify the cause of any observed phone failure.

Finding: in the DEVICE branch, successful `dwc3_core_init_for_resume` followed by a negative `dwc3_gadget_resume` now jumps directly to `out`. That path only releases `detect_pm_busy`. The initialized core/PHY state is not unwound before returning a failure to PM. This makes simple error propagation insufficient as a deployable recovery change.

The exact affected chain is:

| Stage | Actual behavior |
| --- | --- |
| Candidate `core.c:2516` init-for-resume | Deassert optional reset, enable optional clocks, then initialize core/PHY. Only failures inside this helper run its clock/reset unwind. |
| Core init at `core.c:1383,1413` | Initializes generic PHYs and powers them on, with matching exit/power-off operations in `dwc3_core_exit:994`. |
| DEVICE branch `core.c:2666–2673` | After successful init, a gadget error now skips directly to the shared PM-gate exit, without core exit. |
| Gadget `gadget.c:2801–2818,5302–5310` | A soft-reset error can return before reconnect; otherwise event buffers and gadget endpoints/interrupts are started, then RUN_STOP can return ETIMEDOUT. Software `pullups_connected` is set before its successful hardware observation. These return boundaries were already tested by the earlier 126 assertions. |
| Runtime caller `core.c:2769–2796` | A negative common result returns immediately. It performs no resource cleanup. The actual RPM implementation `runtime.c:934–945` sets RPM_SUSPENDED after a failed callback and cancels pending requests; it does not invoke driver suspend to undo the failed resume. |
| System caller `core.c:2849–2874` | On a negative common result it calls `pm_runtime_set_suspended`, re-enables runtime PM and returns. It does not unwind core/PHY. The generic system PM runner logs the failed callback and completes the device; it does not rerun driver suspend as compensation. |
| Actual `qcom,dwc3` legacy parent | Its child `snps,dwc3` is populated as a separate platform device. Legacy parent resume only restores its clocks/interconnect/own status; it does not call or undo child core resume. Parent/child ordering is not a child-resource rollback. |

The cached exact DT source has clocks/reset on the Qualcomm parent and PHYs on the child; the child has no core clock/reset properties. Therefore this board's counterexample uses NULL optional core clock/reset handles. It demonstrates retained PHY/core initialization, not a claim that five child clocks or a child reset physically leaked. The actual clock/reset helper bodies remain included to check the existing unwind control path. The newer `qcom,snps-dwc3` glue also returns a core error without rollback, but that is not the selected board binding and is not an additional deployed-path finding. OTG is disabled in the saved configuration; HOST is outside this review.

`repro-result.json` records only two new actual-function caller sequences and one control under ASan/UBSan/Werror. Nine exact function bodies are included: clock helpers, core exit, init-for-resume, gadget soft-connect/resume, common resume and runtime/system callers. Fake hardware boundaries supply successful core/PHY initialization and a legitimate RUN_STOP timeout. Both new callers leave modeled PHY/core state initialized; the actual system caller also marks runtime suspended. The original init failure control runs its existing unwind and leaves no initialized state. The complete runtime PM machinery, DMA, PHY hardware and IRQ behavior are not simulated; the RPM failure-state conclusion is a separate static check of its exact cached source.

`source-manifest.json` pins narrowly collected callers to original Image source commit `ba61a62293e0f6bc5838c06f2e85e033e3d702a8`. The approved original storage helper located the existing source; no SDK, build, root candidate change, shared write, phone, SSH or USB operation occurred. The author’s build receipt establishes object compilation only; it cannot fill this error-recovery gap.

Suggested next revision, pending review: on the new DEVICE gadget-error path, use a returning same-image gadget-abort helper under the existing connect mutex. Reuse soft-disconnect's active-transfer stop, ensure gadget IRQ/EP0 stop even when pullups are false, and join IRQ before core/event/PHY teardown. Preserve the primary gadget errno and report a distinct abort error; never call gadget-suspend as rollback because it can try reconnect. Pair initialized core state through its existing exit path, including optional clocks/reset. If the OTG-device propagation is retained, its already-installed OTG state also needs the matching exit; leave HOST untouched.

This suggestion is a failure-state design, not a proof that arbitrary HALT failure can safely be ignored or that a resume can automatically recover. The rollback must explicitly handle its own failed HALT/stop observation and the runtime caller's pre-existing pending-event/IRQ-reference early-return semantics. A terminal PM error may still require a separately controlled lifecycle recovery. No patch is added here and no hardware PM trial is proposed.
