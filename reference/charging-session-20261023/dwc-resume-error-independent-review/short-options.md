# Narrow options after the existing resume-error audit

This comparison reuses the original `usb-resume-errors/` 126-assertion audit, frozen DWC R2 and the present caller counterexample. No new candidate, old-suite rerun or hardware PM trial is implied.

| Option | Proven scope and remaining gap |
| --- | --- |
| Keep the existing diagnostic-only patch | Logs the already-returned gadget error while preserving current PM return values, core initialization and IRQ/reference behavior. It avoids introducing a new negative-resume resource/PM mismatch. Logs must describe a callback/gadget error, never physical recovery. It does not automatically recover the data link. |
| Reuse existing recovery synchronously while still powered | `dwc3_gadget_recover_locked` (`R2 gadget.c:5070–5104`) already stops transfers, performs soft-disconnect, synchronizes IRQ, caps reconnect attempts with `err_recovery_count`, and uses soft-connect; failure sets UNRECOVERABLE. A separately reviewed DEVICE-only attempt could run with the current initialized core and retain the diagnostic-only PM return policy. It needs no new failure-field ABI, clock rollback or IRQ parking. This is a plausible smaller behavior candidate, not code implemented or verified here. Exact primary/cleanup diagnostics and the actual bound callbacks must be reviewed before any change. |
| Queue existing error work directly from the PM callback | Not sufficient as an established recovery sequence: `dwc3_err_recovery_work` (`R2 gadget.c:5106–5120`) takes connect_mutex but has no active-PM acquisition or wait for PM callback completion. An ordinary work item may run before common resume finishes SUSPHY restoration and before runtime PM changes RESUMING to ACTIVE. The current worker cannot by itself establish that ordering. Its normal IRQ-driven use is not proof that a new PM-callback caller is safe. |

The recovery count limits reconnect attempts after successful disconnect; it is not a generic retry budget for every failure. A failed disconnect returns before incrementing that count, and existing event scheduling may invoke work again. Neither diagnostic-only nor the current worker guarantees future host enumeration or successful automatic recovery.

Keeping the initialized core with a successful PM callback is consistent with the existing diagnostic-only scope. A synchronous recovery still has behavioral and lock reentry risks: it invokes the existing sleepable disconnect callback under connect_mutex, and a generic callback could request pullup/runtime PM again. The earlier R2 independent review found no such reverse path in the selected configfs NCM callbacks; that bounded observation cannot be generalized to arbitrary gadget functions. No attempt should call gadget-suspend as rollback, because its error path explicitly attempts reconnect.

Sources: `usb-resume-errors/README.md` and its mutually exclusive diagnostic/propagate patches; frozen R2 `gadget.c` SHA `0153f79691ef73473e791341c710d092421213cffbd5fbe07411a00037daa07a`; the exact runtime PM source in this review's source manifest. These are source-level conclusions, not evidence that any particular resume error occurred on the phone.
