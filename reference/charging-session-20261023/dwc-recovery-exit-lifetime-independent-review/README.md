# Independent review: exit-only recovery lifetime

Accepted within the frozen source scope; no additional confirmed defect was found. This review binds UI source delivery `4a645839…26f07`, candidate gadget `f32623e0…40557`, header `b177e605…e62e4` and its eight-case receipt. It reads source, existing receipts and hashes only. It does not import an author module, execute a test, compile, access storage or contact a device.

Only four gadget functions change from the frozen outcome candidate: recovery scheduling, recovery publication, gadget init and gadget exit. The internal outcome bodies and existing recovery/primary policy remain unchanged. Both actual enqueue sites check `recovery_stopping` and call `schedule_work` under the same `dwc->lock` which exit uses to close the gate. A producer already past that lock queues before closure and is covered by the later `cancel_work_sync`; a producer arriving after closure cannot queue. A worker already in its attempt may finish, including publication, while exit waits; its pending publication cannot rearm after closure. The helper's closed-entry receipt initializes pending/reconnected before returning `-ESHUTDOWN`.

Exit releases the spinlock before joining and holds no `connect_mutex` across the join. The worker can therefore acquire/release that mutex and return before resource teardown. The mutex remains alive through `usb_del_gadget`, and is destroyed afterwards. The pinned UDC core (`17d0d78f…1041`) calls `device_del`, maps gadget bus remove to `gadget_unbind_driver`, stops VBUS work, disconnects under its UDC connection lock, disables async callbacks, joins IRQ callbacks, calls function unbind, and invokes the DWC UDC stop for a started UDC. The unchanged DWC stop clears its driver pointer and calls `free_irq` before this delete returns. Disconnect can legitimately skip pullup-off in an unconnected/deactivated/stopped state; the review does not turn every USB delete into proof of an actual hardware stop.

Cached device core (`52247f43…de2c`) supplies `device_del → bus_remove_device`; the synchronous driver removal between those and the cached gadget remove is the existing device-core API contract. Generic bus/dd files are not newly imported. The fake USB delete in the fixture checks boundary ordering and is not the basis for claiming that the real device core unbinds synchronously. The default configfs/NCM callback source scope is reused from the prior fixed-source DWC review; this does not certify arbitrary future gadget drivers or callbacks that synchronously join their own recovery work.

Init resets the gate before publishing the new gadget/work/IRQ lifetime, under the original caller's serialization. No additional producer of `err_recovery_work` was found in the complete candidate file. Parallel double init/exit, unrelated endpoint or PM entry, and init-error cleanup remain outside this exit-only repair. In particular, `recovery_stopping` is not an exclusion gate for the initial connect in the new DEVICE outcome API and is not an abort/PM resource owner.

The existing eight cases include the old late-enqueue/retired-mutex control, two late IRQ boundaries, a queued worker, a closed helper receipt, a real pthread join with a running recovery attempt, open-gate pending publication, old failure policy and the null-gadget no-op. Their GCC/run PIDs 788/797 both reached rc0 with ASan/UBSan and Werror; this review did not rerun them. The fixture's workqueue/IRQ/UDC/MMIO/PM/free boundaries are fake, so its old counterexample does not prove a physical UAF or DMA safety.

The new persistent struct field changes layout and requires consistent future rebuilding of all affected objects. No core consumer or safe DEVICE PM failure unwind is supplied. HALT-unknown, pending IRQ ownership and active MMIO/endpoint producers remain unclosed; this review gives no Image, deployment or physical resume acceptance.
