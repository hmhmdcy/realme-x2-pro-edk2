# Default-off PD5V client bridge — offline candidate

This closes the next real consumer block from `apsd-next-eud-off-closure`. The DWC owner now has an explicitly enabled pre-attach PD5V client: actual same-PMIC binding, first physical off takeover, real context references/cancel-join, then the subsequent sink epoch. **Every APSD window and1341 attempt remains refused** at `owner_entry_gate`: route capability, PHY withdrawal and final-transfer revalidation are still missing. This is not full PD, APSD, fast charging or physical acceptance. No payload was installed and Image501 is unchanged.

`bridge.patch` is the complete delta against the frozen DWC owner and PD5V R2 leaves. Original files/receipts are untouched. `core.c/core.h/gadget.c`, backend header, once core and strict R7 decoder are copied verbatim; the existing DWC lifecycle integration is not rewritten. `unchanged-functions.json` identifies the unchanged PD control/lifetime bodies, including the four-write sequence, stability/freshness, validation, release, quiesce and error policies.

## Actual binding and state

The new default-n `USB_DWC3_SAMURAI_APSD_PD5V_CLIENT` option requires the existing owner, OF and **TYPEC_TCPM=y / TYPEC_QCOM_PMIC=y**. The current actual TYPEC_QCOM_PMIC=m is explicitly refused in code. No EXPORT/UAPI/ko workaround is added. It also requires existing `samurai,apsd-owner`, new `samurai,apsd-pd5v-bridge`, a real `samurai,apsd-typec` phandle, and the PD5V driver's existing double opt-in. No DT/parameter activation is performed here.

`qcom_pmic_typec_5v_status(actual_typec, actual_source, status)` is the only new provider API. It resolves the actual bound PD5V instance and verifies both exact parent-device and regmap identity with the registered R7 provider. It returns binding ID, initialized/blocked/error **metadata only**, with zero register, power or protocol I/O. A registry-protected binding serial never reuses an ID and refuses overflow. Initialized=false/true is not a permission: only real acquire+validate grants the disabled-PD lease. Wrong parent/regmap, removed or missing bindings remain errors; a not-yet-bound supplier can be observed again without creating an epoch or writing.

The real worker follows `WAIT_BINDING → WAIT_FIRST_OFF → WAIT_ATTACH → SINK_EPOCH`. A present source at boot cannot initialize PD or create an eligible once epoch. On a new actual backend off observation, R2 acquire executes its stronger vSafe0V/stable-off checks, takes the shared supply reference and performs the original four disabling zero writes/readbacks. The lease stays held through a later fresh attachment; strict R7 sink/error/CC qualification precedes the once core. The remaining gate returns EOPNOTSUPP before EUD/DWC/PHY begin or any1341 transfer.

Real detach resets only the once protocol phase. UDC stop/rebind and PM pause/reacquire preserve attempted history and the established off fact for the same PD binding; replacing the PD instance requires another actual off. Backend re-registration/new sample serial cannot reset an attempted physical session. Metadata→acquire→metadata checks prevent a remove/reprobe winner from inheriting another instance's off history. Cancellation is checked before acquisition and after a joined in-flight acquisition; a completed off takeover remains a recorded fact even when the parent then cancels.

## Lifetime, PM and errors

The owner has a real kref. PD5V client get/put pins the owner/context, and final put releases the held Type-C device reference before freeing the owner. PD5V R2 takes its primary lease reference and extra quiesce reference using those operations. Its callback runs outside PD locks, takes the owner registry only for lifecycle serialization, publishes abort and joins the exact worker before releasing its lease. The worker never takes the owner registry. Unbind joins/unregisters first, saves histories, nulls the DWC pointer and drops its base kref; a late pinned callback cannot use removed DWC MMIO and survives until its final put. Failed restore/orphan retains ownership rather than claiming release.

PD cancellation clears only its own temporary fence; it cannot clear system/runtime/UDC fences. While the Type-C owner remains blocked, delayed work can read metadata but cannot acquire or perform PD I/O. Complete merely revalidates R2 control state. A PM revocation racing with validate is cancellation only when fresh metadata proves that same binding blocked with no actual error. R2 power/write/readback/validation errors stay sticky; the bridge's FAILED phase does not retry them after resume, polls or detach. `pd_error` retains the last nonzero diagnostic; phase and the real provider error distinguish a historical cancellation/wait from a fault. No existing charge fault, budget or telemetry is rewritten.

The bridge does not infer PD inactive from DT disabled, PHY enable0 or absent TCPM. It takes actual disabling control only in its explicit limited mode. It does not grant EUD-off routing, USB2 high-Z, a5V voltage guarantee, full Type-C/PD negotiation/PR swap/hard reset, VOOC/FFC ownership, native current or charging permission.
