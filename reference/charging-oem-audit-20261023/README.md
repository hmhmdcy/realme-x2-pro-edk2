# 原厂普通充电策略缺口审查

2026-10-23。纯离线审查，未访问手机、SSH 或相机 SDK，未修改充电实现、共享内核源码及 build。审查的当前文件哈希、原厂缓存路径、编译命令和实际输出见 [audit.json](audit.json)。本报告只证明所列源码行为及差异；不代替电池的温区、低压预充、完整终止／再充物理验收。

原厂来源为已缓存的 [Realme Android R 固定提交](https://github.com/realme-kernel-opensource/realmeX2pro-X3-AndroidR-kernel-source/tree/23172a1571bd91156032cc9fef16284a82b63d2c)，没有重新下载。下列 `oplus_charger.c` 行号均对应 `drivers/power/oppo/oplus_charger.c`，19781 DTS 指 `arch/arm64/boot/dts/19781/pm8150b.dtsi`；完整本地路径及 SHA 在 audit.json。

## 应先修复的两项实际缺口

### 温度正常后仍被永久锁停

当前 [mp2650-core.h](../charging-management-20261023/mp2650-core.h) 37–40 行的 `sm_sample_latch` 把任何非源预算错误锁存，77–79 行在无合适温区时返回 `-ERANGE`；[samurai-mp2650.c](../charging-management-20261023/samurai-mp2650.c) 159–165 行直接将它锁存。只有 109 行的真实断开或 323 行显式 AUTO 才清零。因而温度单次达到 53℃后，即使回到 25℃、所有保护新鲜正常，仍不能自动恢复。

原厂 `oplus_charger.c` 5664–5675 行在温度恢复后撤销 `BATTTEMP_ABNORMAL` voter；4174–4266 行有温度方向和当前温区相关的 2℃防抖、0℃附近 0.5℃防抖，4271–4336 行负责归类和切换。真实温控拒绝应与电气／总线错误锁存分别记录。

最小接入建议：保持有效域外立即停充，但把明确由温度越界造成的暂停作为可恢复抑制；恢复需新鲜、有效、全部保护通过的数据和温度迟滞。不要把所有 `-ERANGE` 都当可恢复温控错误，因为同错误码还覆盖电芯合理域与目标参数错误。不要让温度恢复清掉已有 Safety/PF、REG14、传输或写入故障锁存。

[独立探针](probe-current-policy.c) 已直接编译当前生产核心，在 ASan/UBSan 下复现 `temperature_recovered_policy_ret=0 target_enable=1 latched=1`。这证明当前缺口，并非修复后通过。

### 连续接线满 10 小时会把 Full／正常再充锁死

当前驱动 114–118 行在 attach 后按 BOOTTIME 计 `session_seconds`；仅真实断开清除 session；没有把充电器 Full 状态纳入该会话状态机。核心 58–59 行到 36000 秒无条件 `-ETIME`，随后成为永久锁存。已满电插在电脑上一夜也会触发，用户需要拔插或显式 AUTO 才能恢复。

原厂 `oplus_charger.c` 4539–4559 行的 36000 秒限制针对 `total_time`，但 `full_action` 5306–5318 行每次满电会把 `total_time=0`，而 6925–6947 行只在下一段周期重新积算。其 `check_status_full` 6754–6757 行即使已是 FULL 状态仍执行 full_action；保护检查／Full 处理／其它计时的顺序见 7351–7378 行。不能把这个原厂限制直接解释成“每次插线最多十小时”。

最小接入建议：建立实际充电周期而非 attach 的限时；在已确认正常终止／Full 后终结本轮计时，在满足再充条件后建立新周期；保留未完成周期的累积限时，短暂 USB 重置、暂停、休眠不能持续擦掉同一轮安全时间。真实超时仍锁停。仅用用户态 SOC=100 或一次电流为零重置计时不充分。

独立探针直接给出 `attached_35999s_ret=0 target_enable=1`、`attached_36000s_ret=-62 target_enable=0`。驱动未因 Full 重置的事实由 102–118 行和全文件 `session_start` 的赋值点确认。

## 原厂软件终止／再充与当前硬件方案的差异

19781 DTS 400 行明确启用 `qcom,check_batt_full_by_sw`，399 行 `suspend_after_full` 是注释。原厂 `turn_on_charging` 4014–4015 行会关闭硬件终止；`full_action` 经 4134–4149 行 FULL voter 关闭普通充电。当前核心则保留硬件终止与安全计时，以 100mA 硬件终止、100mV/节硬件再充工作。这是有意的保守替代，不能称为完整复刻原厂终止／再充逻辑。

原厂可直接复用的具体策略：

| 行为 | 原厂依据 | 应保留的语义 |
| --- | --- | --- |
| 软件 Full | DTS 332–337；oplus_charger.c 6435–6495 | 单芯最大电压超过冷区3.930V、0–44℃各区4.350V、暖区4.080V；净充入电流不大于110mA时连续超过5个5秒样本，或电流非充入时连续超过10个样本 |
| 电压后备 Full | oplus_charger.c 6498–6552 | 温区目标加硬件增量，连续4样本；不能直接用此实现来提高当前继承电压 |
| 再充 | oplus_charger.c 5260–5303 | 冷区目标减300mV，微冷区减200mV，其他区减100mV；单芯最大电压连续超过5个周期低于门限，且无 short-c 禁止再充 |
| 电压定义 | oplus_bq27541.c 408–432、2468–2490 | 两芯机型的 `batt_volt` 返回两芯最大值，并非整包或平均值 |
| 硬件预充 | oplus_mp2650.c 744–770、1724–1726；当前 datasheet-evidence.json | OEM 选择整包6.6V预充阈值；当前依官方 MPS 表配置预充180mA，不能拿 OEM 旧算式覆盖已核对的寄存器编码 |

建议在最小修复中保留现有硬件终止和安全计时作为后备，再加入必要的软件 Full／再充周期管理。所有阈值必须受当前已采用的单芯4.3625V及温区降压限制；不要为匹配表格抬高电压，也不要让软件再充在硬件已判故障、保护状态不明、TCA 请求停止时反复重新使能。采集净电流应使用已核对的 gauge 0x0C 有符号电流，不能使用输入电流或 current cap。原厂 5 秒周期计数若移到当前 1 秒轮询，需以时间或等效节拍实现，不能直接复制计数6／11。

## TCA 不能简单等同永久电气故障

当前核心 56 行将 `gauge_flags & 0xc000` 统称 `-EIO` 并永久锁停。已缓存官方 TI SLUUA65E 第27页 §4.8（ti-manual-private.txt 1207–1215 行）说明 TCA 不仅由 OCC/COV/OTC 触发，也会由 `GaugingStatus.TC && CHARGE mode` 触发；第70页 §12.1.6（txt 2925–2930 行）给出 TCA bit14、OCA bit15。`FC` 则是 bit5（txt 2899–2901），不是 bit9。

本机报告 factory 0x2719，不能仅凭 TI 2610 文档断言所有内部算法一致。可在上述周期状态机中保留 TCA 停充请求，并结合实物 Safety/PF/Operation、正常 Full 与恢复数据分类，而不是删掉 TCA 检查或一见温度正常就强行恢复。当前白名单 MAC 报文校验及不写保护 FET/NVM 的边界应保持。

## 不应照搬的原厂初始化

原厂 `oplus_mp2650.c` 1698–1755 行包含复位、关闭硬件终止、安全超时禁用、OTG及40秒看门狗初始化；普通充电 Linux 适配没有理由整段重放。现有核心 146–147 行拒绝活动看门狗、要求终止和安全计时开启，204–210 行已按官方 MPS 表配置预充／终止／再充编码，本次审查没有得到需要取消这些保护的证据。不能以 OEM 提取优先为由恢复原厂针对 Android 后台管理器的危险初始化假设。
