# APSD next closure after the actual EUD-off boot

The next implementable block is a **real PD5V client bridge with a pre-attach preparation phase**, using the existing R2 acquire/validate/release API. It must acquire control during a new physical off/vSafe0V window, before accepting the subsequent attachment as eligible. Replacing the existing `owner_entry_gate()` with an acquire call at the old location cannot work: that location is reached only after a present source has produced SDP/CDP DONE, while first PD5V takeover explicitly requires physical off. This is an integration-order defect in the proposed combination, not a defect in the currently disabled components or the running R8 charging path.

This leaf is source analysis/design only. It changes no candidate, shared source, config, payload or device. No test, build, SDK, Git, phone, SSH or USB operation was run. Session confirmed there is no newer owner/backend implementation after the frozen leaves. Image501 and the active icon work supply none of these missing APIs and remain independent.

## Minimal next block: PD5V bridge, still no APSD transfer

Implement this first in a new revision of the DWC owner, default off, using the frozen PD5V R2 API. It is a real acquisition/cancellation consumer, not a replacement permission Boolean. The remaining route/PHY/write gates must continue to refuse a hardware detection attempt until their own contracts exist.

1. Resolve one explicitly linked **actual** `qcom,pm8150b-typec` device and the actual R7 provider. Verify their same parent PMIC/regmap identity and the board's existing 1500/1700/supply binding. An instance generation is separate from sample serial and the physical once epoch. Missing/unbound/mismatched components give a concrete error, never inactive=false. Current DT Type-C is disabled, so there is presently no device to acquire from.
2. Introduce `WAIT_FIRST_OFF` before `samurai_apsd_attach`. A complete new backend off sample can initiate `qcom_pmic_typec_5v_acquire`; R2 itself verifies its stronger vSafe0V, sink-only/QC-off policy, 500ms stability, fresh pre/post observations and four disable readbacks. This can run while DWC is inactive; it must not invoke DWC/USB2 resume or PHY init. A source present at boot remains waiting for a genuine off window. No inherited boot contract is declared gone because the source already looks SDP.
3. A successful lease enters `PD_DISABLED_WAIT_ATTACH`. Retain it until cancellation/lifecycle release. Only a later new physical all-on sink observation can create the eligible once epoch. Use `samurai_usb_decode`'s existing seven-field sink/error/noncompliance/CC checks; a known sink may legitimately have APSD DONE clear while waiting for the new result. Exact SDP/CDP/no-QC remains the once-core request condition. Wire presence alone is insufficient.
4. Use a real owner kref for PD5V client `get_unless_zero/put`. Its `cancel_join` first publishes abort, joins this exact worker outside PD5V/component locks, unwinds owned windows if any, and releases the lease. It must not be called while owning the worker itself, must not hold `input->lock`, and must preserve the existing rule that a worker never waits for `owner_registry`. Do not keep the current unconditional `kfree(o)` after introducing a live PD client reference.
5. A true detach resets the APSD once history, not a failed/unknown PD control transaction. UDC stop/rebind does not create a physical epoch. PM prepare cancels/joins and releases; complete only verifies the retained disabled state, never enables or retries PD writes. Preserve the established physical history when reacquiring after a normal lifecycle pause. Any error after power takeover/write remains the R2 binding's real error, not an automatic retry on the next poll.

State outline: `opt-out → no I/O`; opt-in `WAIT_BINDING → WAIT_FIRST_OFF → PD_DISABLED_WAIT_ATTACH → NEW_SINK_EPOCH → EXACT_SDP/CDP_READY`. At the end of this block the latter still reports the specific missing route/PHY/write-boundary coverage; it performs **no1341 transfer**. This is useful incremental implementation because it closes a real owner/lease/cancel path and a demonstrable ordering mismatch while keeping incomplete analog coordination disabled.

The existing `CONFIG_TYPEC_QCOM_PMIC=m` cannot satisfy DWC built-in calls to these unexported functions. The actual compound object is `qcom_pmic_tcpm.o` (`pd5v-owner-context-r2/Makefile`), and the double opt-in uses `samurai_5v_only` plus `realme,pd5v-only`. A future same-Image integration must explicitly choose built-in linkage and its dependencies, new reviewed board binding and consumer option; the R1 design DT fragment intentionally remains disabled. It is not a new ko installation path and is not part of Image501.

## Remaining blocks before the first permitted APSD command

**EUD-off route contract.** Actual `usb500-r8-eud-off-result.json` records a direct root-hub NCM topology and accepted native500; the completed icon capture confirms source/native/hardware500 after a real reconnect. This removes the *observed EUD intermediate hub* from that boot's USB data path. It does not provide a kernel lease that owns EUD routing across PM/reprobe or proves Type-C/PD inactive. The R2 firmware handoff's complete CSR0 receipt and disabled COM/no-producer policy are stronger static inputs than absence alone, but no present kernel API binds those inputs to an exclusive, revocable route capability. The next owner revision needs an explicit boot-disabled-route mode/supplier contract, distinct from COM software quiet; it must verify the actual trusted boot policy/binding and exclude/revoke on a new EUD producer. Do not call an absent COM API, invent a cookie, make ENODEV mean success, use full `qcom_eud` as a substitute, or reread/write active CSR from this offline task. Establish that contract before bypassing EUD runtime calls. Dynamic EUD/role operation remains a separate path.

**PHY withdrawal.** The current PHY window guards `.init/.exit/.set_mode` and runtime callbacks under `phy->mutex`, but its platform driver has no explicit remove/shutdown consumer join. Add one actual provider publication/withdrawal contract with real client lifetime pinning. Withdrawal must revoke new entry first and call cancel/join outside `phy->mutex` before devres releases MMIO/clocks. If exact restoration fails on forced removal, record revocation/failed restoration and forbid further access to removed MMIO; a saved token/get_device reference is not permission to retry after devres. Do not infer PM/remove closure from the existing successful begin/end tests.

**Final transfer boundary.** Preserve `regmap_write_bits(1341,bit0,bit0)` and consume the physical epoch before a possible transfer. A future narrow backend revision must support a real bound attempt identity plus fresh stable seven-field reread and final cancellation/lease-generation validation immediately before that one write, while not holding cross-component locks across joins. The current owner calls `owner_entry_gate` before claim, then enters `rerun_once`; its abort check alone leaves a check-to-write interval. Revocation must publish before join, and join must cover a transfer already begun. Physical detach can still race between regmap accesses; post mismatch is failure/unknown, never an atomic off/attached guarantee. Provider unregister/re-register must not reset attempts through a new serial counter.

After these are implemented together, the reusable operational sequence is: real PD-disabled lease + fresh sink epoch + route capability → active DWC HALT → initialized PHY high-Z → new stable source/lease check → consume once epoch → one1341 transfer → observe **new** DONE-clear then DONE-set → PHY exact restore → DWC restore → release route/PD ownership. Errors/cancellation restore in that order and preserve independent primary/restore errors. The once core's WAIT_CLEAR/WAIT_DONE handles old-DONE rejection; the current owner's100ms sampling/5s deadline are engineering choices and not proven PMIC timings. A missed brief clear must fail, not trigger a second command or fabricate completion.

## Original behavior and current scope

The fixed same-handset OEM sources already give the required choreography: `smb5-lib.c:1033` request_dpdm avoids PR-swap; plugin5080/5113 acquires DPDM; source IRQ5458/5512 consumes the per-attach rerun flag before its one SDP/CDP command; detach5158 clears that flag. `phy-msm-snps-hs.c:633` performs the three high-Z operations; disable672 does not supply an exact saved-state restoration. OEM `smblib_set_prop_pd_active:4319` receives a real protocol state and disables APSD during PD. The new once core intentionally improves their failure/new-DONE semantics; the old void write/error handling is not to be copied.

The current ordinary SDP500 path is working in its observed window. A source remaining SDP is not a demonstrated classification failure, and an APSD result cannot grant native500. Recovered one-shot APSD is still a missing OEM behavior, not a reason to disturb a healthy current connection. PD5V is a narrow explicitly PD-disabled ordinary-input mode; it supplies neither PD negotiation/PR swap/hard reset support nor VOOC/SuperVOOC/FFC ownership, and cannot guarantee every external source is5V. Complete TCPM support remains the separate real-state/ingress-invalidation/qcom-pre-reset-join work specified in `apsd-tcpm-owner-candidate`. The limited bridge can be implemented first; completing it does not complete the full charging/Type-C goal.
