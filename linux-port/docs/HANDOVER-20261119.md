## Next device step (requires the user)

### Known open issue: `apk upgrade` exit code

On the delivered image `apk upgrade` performs the real upgrade (for example
`libcrypto3`/`libssl3` 3.5.9-r0 → 3.5.9-r1 land both in
`lib/apk/db/installed` and on disk) but still prints `1 error; ... in 1245
packages` and exits 1.

What was ruled out with direct experiments:

- The 15 board packages missing from a repository index. Exporting a signed
  local index now works (`export-apk-repository.py` exports 22 APKs and
  `apk policy samurai-platform` resolves it from `@samurai /var/lib/samurai/apk`),
  the "no longer available from a repository" note disappears, and the error
  still occurs.
- `postmarketos-mkinitfs` exiting 1 on `found: []`. Replacing the binary with a
  stub that exits 0 does not change the outcome, so apk is not invoking it in
  this transaction.
- The trigger list (`lib/apk/db/triggers` emptied), `scripts.tar.gz`, and
  `etc/apk/commit_hooks.d` were each removed in turn; the error persists.
- The installed database structure: 1245 records, all starting with `C:`, no
  duplicates, no missing files or changed checksums for `postmarketos-mkinitfs`.
- `world` checksum pins were cleared in the test copy; the error persists.
- It reproduces with the image's own aarch64 `apk` and with a static x86_64
  `apk-tools 3.0.9-r0`, so it is not a qemu-user artefact.

A fresh empty root installs `nano` with `OK` and exit 0 using the same apk, so
the difference is in this image's state rather than in the tool or the
repositories. It does not block the upgrade itself, but the non-zero exit code
will break scripts that check the status.

### Root cause (found and fixed in the `apps2` rebuild)

`apk` returns exactly one error because one installed record carries a
`f:s` (broken_script) flag:

    P:postmarketos-mkinitfs
    f:s

`src/commit.c` loads that flag into `ipkg->broken_script` and folds it into the
per-change error counter, so every transaction reports `1 error` regardless of
what was actually installed. `apk fix` shows the same package, which is why an
empty root and an empty `nano` install both look healthy.

The flag exists because the mkinitfs apk trigger exited 1 during the image
build. Two upstream facts make it fail on this device, which boots an external
EDK2 kernel:

1. `internal/osutil/osutil.go` in `postmarketos-mkinitfs` locates the kernel
   through `/usr/share/kernel/<flavor>/kernel.release` and refuses to continue
   unless exactly one such file exists. The upstream `linux-*` packages install
   it; this rootfs has `kernel-none`, so the directory was missing and mkinitfs
   printed `only one kernel release/flavor is supported, found: []`.
2. Meeting that requirement alone is not enough: mkinitfs then calls
   `boot-deploy`, which aborts with `No kernel found in /boot (checked:
   vmlinuz*, linux.efi)` because the kernel lives in the EDK2 payload, not in
   this rootfs.

The fix follows the design this port already documents for `kernel=none`
(`ROOTFS-F2FS-IMAGE.md`: the generic mkinitfs step is skipped and the boot
chain mounts the F2FS rootfs directly). It uses mkinitfs' own supported switch
rather than inventing state:

- `finalize-plasma-rootfs.py` rewrites the packaged mkinitfs trigger to end
  with `KERNEL_INSTALL_BYPASS=1 /usr/sbin/mkinitfs`. Upstream mkinitfs prints
  `KERNEL_INSTALL_BYPASS set to '1'. Skipping mkinitfs.` and exits 0.
- The rewrite is gated on the board package's own
  `/usr/share/samurai/external-kernel.txt` marker, so an image that does need
  an initramfs is never silently skipped.
- It also removes the stale `f:s` flag the pre-fix build left behind.

Direct check of the trigger script inside the image root: with the guard it
exits 0; with the guard removed it still exits 1 with `found: []`, so the
result comes from the guard and not from a cleared database flag. Verified on
the delivered image with its own aarch64 `apk`: `apk upgrade --simulate` and
`apk fix --simulate` both print `OK: 2938.6 MiB in 1245 packages`, and no `f:`
flags remain.

`export-apk-repository.py` was fixed on the way: the build workspace index
keeps several `pkgrel`s per name, which used to abort the export with
"Multiple versions in index". It now exports only the version recorded in the
installed database.

The image should not be described as "clean `apk upgrade`" until this exits 0.

1. Hold Power ~15 s to force off, then power on normally (or go to ColorOS
   recovery with Vol-Down + Power if flashing directly).
2. In recovery run
   `powershell -NoProfile -ExecutionPolicy Bypass -File
   linux-port/scripts/flash-plasma-rootfs-adb.ps1 -Confirm:$true -Reboot`.
   It verifies the local image hash, requires a root adb shell with
   `simg2img`, checks device free space, pushes 128 MB chunks with per-chunk
   size checks, verifies SHA256 on the device, then runs `simg2img` into
   `/dev/block/by-name/userdata` and waits for it to finish.
3. Do NOT use fastboot: its 5 s write timeout wedges the channel.
4. Do NOT `systemctl restart samurai-radio` or write `stop` to
   `/sys/class/remoteproc/remoteproc1/state`; that tears down Wi-Fi and the USB
   gadget together and loses NCM/SSH.
