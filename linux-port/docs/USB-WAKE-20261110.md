# USB 唤醒分层适配（2026-11-10）

## 结论先行

有，而且可以只使用 Linux 已有的标准模型，但必须把三种“USB 唤醒”分开：

| 场景 | 标准模型 | 当前状态 |
| --- | --- | --- |
| 手机 suspend 时插拔 USB 线/充电器 | `extcon-usb-gpio` + PM8150 GPIO10 + udev `power/wakeup` 策略 | 离线 DTB 和 rootfs 候选已完成，待真机 suspend 验收 |
| 同一根线已连接，主机发 USB resume 唤回手机 | DWC3 peripheral/gadget + QUSB2/DP/DM PDC wake IRQ | U3-only 标准分层候选已上机；Windows NCM 不进入 selective suspend，待 Linux host autosuspend 验收，见 [USB-HOST-RESUME-20261110](USB-HOST-RESUME-20261110.md) |
| Type-C dock/PD/外设唤醒或 host role | PM8150B TCPM + `usb-role-switch` + dual-role/xHCI | 属于后续 dual-role 层，未在此候选内 |

因此本层解决的是“插线或拔线能把手机从 suspend 唤醒”，不声称
“NCM 在 suspend 期间保持在线”，也不声称“主机发一个包或 magic packet
就能唤醒”。手机唤醒后 USB gadget 会重新连接，主机可能需要重新枚举。

## 2026-11-10 真机接入状态

只替换 DTB FFS 的 boot carrier `62dee7b9...` 已写入真机并通过普通重启。
启动后 `/proc/device-tree/extcon-usb1` 存在，
`linux,extcon-usb-gpio` 已 probe，`power/wakeup=enabled`，IRQ 120 显示为
`spmi-gpio` 的 extcon 中断。该证据只确认唤醒源接入，尚未完成 suspend
后的插拔线验收。

同一启动还暴露出内核 release 与 rootfs 模块目录的 `+` 后缀错配，导致
`socinfo`、RTC、Bluetooth 和 zram 模块不可用；在这种情况下进行 suspend
测试会混合多个故障。下一次会话必须先修复同源模块树，再按本文顺序测试。
完整证据、其他服务错误和锁屏后的 DRM `Atomic commit failed: EBUSY` 见
[`BOOT-ERROR-TRIAGE-20261110.md`](BOOT-ERROR-TRIAGE-20261110.md)。

## 硬件证据

Android 真机的实际运行 DT 不是源码中的条件编译注释，而是：

```dts
extcon_usb1 {
    compatible = "linux,extcon-usb-gpio";
    vbus-gpio = <&pm8150_gpios 10 GPIO_ACTIVE_HIGH>;
};
```

同一台机器的 `/proc/interrupts` 有：

```text
pmic_arb ... vendor:extcon_usb1
```

Android 还创建了该平台的 `wakeup11` 节点。PM8150 GPIO10 的 pinctrl 为
`input-enable`、`bias-pull-down`、1.8 V 供电。这说明 VBUS 检测是真实
接入的板级硬件，不是从 OnePlus 或其它 SM8150 机型照搬的节点。

RMX1931 stock DTBO 没有 FSA4480；本层也不引入 FSA4480、SBU mux 或
DisplayPort 假设。

## 分层实现

### L2：板级 DT

候选 overlay：
[`usb2-vbus-wake.dtso`](../dts/experiments/usb2-vbus-wake.dtso)

它只做两件事：

1. 在根节点增加 `extcon-usb1`，绑定 PM8150 GPIO10 的 `vbus-gpios`；
2. 增加 GPIO10 的标准 pinctrl 状态；

SPMI bus 的 PDC 路由不再放在板级 overlay。`sm8150.dtsi` 的
`spmi_bus` 直接使用 `interrupts-extended = <&pdc 1 ...>`，与 SM8250
主线写法一致；这是 SoC 集成，不属于 RMX1931 板级差异。`spmi-pmic-arb`
的 `qpnpint_irq_set_wake()` 会把子 IRQ 的 wake 请求转给 bus IRQ；只有
bus IRQ 位于 PDC 上，PMIC GPIO 的 `extcon-usb-gpio` wake 才能进入
Qualcomm PDC 的睡眠唤醒路径。

该候选不修改 `dr_mode`、DWC3 PHY、NCM gadget、Type-C role 或 VBUS
source；合并结果相对 production base 只有：

- 新增 `/extcon-usb1`；
- 新增 `/soc@0/spmi@c440000/pmic@0/gpio@c000/usb2-vbus-det-default-state`。

`spmi@c440000` 的 `interrupts` → `interrupts-extended` 已进入
`sm8150.dtsi`，属于 SoC 基线，不再计入板级 overlay 的语义差分。

### L3：内核

使用的都是内核已有驱动：

- `CONFIG_EXTCON_USB_GPIO=y`；
- `CONFIG_PINCTRL_QCOM_SPMI_PMIC=y`；
- `CONFIG_QCOM_PDC=y`；
- `CONFIG_PM_SLEEP=y`；
- `CONFIG_USB_DWC3_GADGET=y`。

没有新增板级 USB 驱动，也没有把手机私有 GPIO 操作塞进 DWC3。

上游当前的 `linux,extcon-usb-gpio.yaml` 使用
`additionalProperties: false`，且没有 `wakeup-source` 属性。驱动只在
probe 时调用 `device_set_wakeup_capable()`，本身不读取
`wakeup-source`；在 DTB 里写这个属性既无效，也会让 dtbs_check 失败。
因此本候选不携带该属性，唤醒启用完全由标准 `power/wakeup` 用户态
策略负责。

### L4/L5：用户空间策略

extcon 设备出现后由用户空间决定是否默认启用；rootfs 只增加一条标准
udev 规则：

```udev
ACTION=="add", SUBSYSTEM=="platform", DRIVERS=="extcon-usb-gpio", ATTR{power/wakeup}="enabled"
```

这等价于在设备出现后执行：

```sh
echo enabled > /sys/bus/platform/devices/extcon-usb1/power/wakeup
```

不使用自定义常驻服务，不修改 `sleep-inhibitor` 插件，不修改 KDE
PowerDevil 默认值。

## 真机验收

更新后的 `samurai-platform` 包把规则安装到
`/usr/lib/udev/rules.d/99-realme-rmx1931-usb-wake.rules`。在安装包之前，
第一轮只做 DTB 验证时可手动执行一次：

```sh
echo enabled > /sys/bus/platform/devices/extcon-usb1/power/wakeup
```

只读门禁：

```sh
sh linux-port/scripts/check-usb-wake-baseline.sh --require-enabled
cat /proc/interrupts | grep extcon-usb1
cat /sys/power/wakeup_count
cat /sys/kernel/debug/suspend_stats/success
```

建议测试顺序：

1. 备份当前 kernel FAT 的 `/Image`、`/samurai.dtb` 和回读哈希；
2. 只替换 `/samurai.dtb` 为 wake DTB，Image/boot 不动；
3. 普通重启，确认 `taint=0`、UDC/NCM、Wi-Fi SSH 和基线门禁；
4. 断开 USB 线，建立一个人工可控的 suspend 窗口（保留电源键或串口恢复）；
5. 用 `SAMURAI_ALLOW_SUSPEND=1 rtcwake -m mem -s 120` 或等效的
   recoverable 路径进入 suspend；
6. 在 RTC 到期前插入 USB 线，确认手机被 VBUS IRQ 唤醒，而不是被
   RTC 唤醒；
7. 唤醒后记录：

   ```sh
   cat /proc/sys/kernel/random/boot_id
   cat /sys/power/pm_wakeup_irq
   cat /sys/kernel/debug/suspend_stats/success
   grep extcon-usb1 /sys/kernel/debug/wakeup_sources
   dmesg | grep -Ei 'extcon|spmi|pdc|dwc3|wake'
   ```

8. 再测拔线唤醒和正反插各一次；如果只有插线有效，只记录插线通过，
   不把拔线写成通过。

成功判据是：`boot_id` 不变、`suspend_stats/success` 增加、
`pm_wakeup_irq` 或 `wakeup_sources` 显示 VBUS/extcon 事件、并且系统
恢复后没有新的 WARN/Oops 或 DWC3 fault。RTC 到期导致的唤醒不能算
USB wake 成功。

## 同线 USB resume 的标准实现

同线 host-resume 已作为独立层落盘，不再和 extcon/GPIO 插拔唤醒混在
一起：

- DWC3 core backport 未合并 RFC 的
  `snps,gadget-keep-connect-sys-sleep` 语义；只在本板显式启用；
- 只有 gadget 已连接且 link 已进入 `Suspend/U3` 时才允许系统睡眠，
  否则返回 `-EBUSY`，避免在无法处理 USB 事务时睡下去；
- Qcom glue 在 peripheral role 布防已有的 DP/DM/SS PDC wake IRQ，
  并在 keep-connect 期间保留 USB clocks/interconnect；
- 板级 DTS 只增加 `wakeup-source` 和 keep-connect 属性，没有新增
  板级 USB 驱动。

当前新 boot 已上机，属性、`power/wakeup`、UDC/NCM 和模块均正常；
活跃链路下的 `s2idle` 被内核以 `dwc3_qcom_pm_suspend returns -16`
正确拒绝。Windows `UsbNcm` 主机长期保持 link `On/U0`，所以还没有
取得一次 host resume 成功样本。设计、产物、测试步骤和回滚见
[USB-HOST-RESUME-20261110](USB-HOST-RESUME-20261110.md)。
