# postmarketOS USB 栈与模式适配（2026-11-12）

本文记录 RMX1931 从板级私有 NCM 脚本迁移到 postmarketOS 标准
USB 栈后的实现、实机证据和未验收边界。结论日期是 2026-11-12；
历史 `samurai-usb` 说明仍见 [USB-NCM-SSH](USB-NCM-SSH.md) 和
[HARDWARE-STATUS](HARDWARE-STATUS.md)。

## 结论

- 运行时 gadget 所有者已切换为发行版 `usb-signaller`：configfs、
  UDC 绑定、`com.meego.usb_moded` D-Bus 和模式服务都由它管理。
- NetworkManager 管理 Developer/Tethering 的 `usb0`；标准
  `unudhcpd` 提供 `172.16.42.1`/`172.16.42.2`；`umtprd` 管理 MTP
  FunctionFS。
- 板级差异只放在：

  ```text
  /etc/usb-signaller.d/90-samurai.toml
  /etc/unudhcpd.conf
  /etc/conf.d/unudhcpd
  ```

  没有新增 USB 传输层、私有 ioctl、GPIO10 extcon 或
  `keep-connect`。
- `samurai-usb-recover` 仍只负责 SM8150 DWC3 控制器的有界恢复，
  但现在会通过标准 usb-moded D-Bus 保存/恢复当前模式，并重启对应的
  usb-signaller 模式服务。它不替代 usb-signaller 的模式管理。
- 当前内核仍是 `CONFIG_USB_DWC3_GADGET=y`、
  `CONFIG_USB_DWC3_DUAL_ROLE` 未启用、`CONFIG_USB_XHCI_HCD` 未启用；
  因此本页只覆盖 device/gadget，不声明 OTG host。

## 分层边界

| 层 | 所有者与接口 | 板级内容 |
| --- | --- | --- |
| gadget 与模式 | `usb-signaller`、configfs、`com.meego.usb_moded` | 只提供 VID/PID、字符串、class、功率和 NCM `qmult` 覆盖 |
| IP 与 DHCP | NetworkManager、标准 `unudhcpd`、标准 OpenRC 服务 | 只选择 `172.16.42.1/16`、`172.16.42.2` 和 Tethering `10.42.0.1/24` |
| MTP | `umtprd`、FunctionFS | 只提供 `0525:a4a2` 描述符 |
| 控制器恢复 | `/sys/bus/platform/drivers/dwc3-qcom/{unbind,bind}`、`/sys/class/udc/*/soft_connect`、usb-moded D-Bus | SM8150 有界恢复策略，最多两次并记录日志 |
| 内核 | 主线 DWC3 gadget、`f_ncm`/`u_ether`、PM8150B Type-C | 不引入 GPIO10 extcon、`keep-connect` 或私有 USB ABI |

恢复服务只在 VBUS 在线、模式为 Developer/Tethering 且本次会话曾成功
枚举时工作。它不能把 suspend 期间已撤销的 gadget pull-up 变成在线
链路，也不能替代物理插拔或同线 host-resume。

| samurai-platform APK SHA-256 | `61145f0f7ab762044deb931977d3501c4cc1a0d93204a487cd4d850ed23c232a` |

`usb-signaller` 的本地补丁位于
`linux-port/packages/usb-signaller/`：

- `0001-gadget-support-board-descriptor-overrides.patch`：板级
  VID/PID、product/configuration、class、MaxPower、NCM `qmult` 覆盖；
- `0002-usb-signaller-network-ownership.patch`：读取
  `/etc/unudhcpd.conf`，并确保 NetworkManager 重新管理 `usb0`；
- `0003-usb-signaller-wait-for-network.patch`：等 `usb0` 出现并重试
  `nmcli connection up`，避免 gadget 刚绑定、主机还没拉起 carrier
  时把默认模式误降为 charging-only。

补丁源锁定与哈希在
`linux-port/packages/usb-signaller/source-lock.json`。板级恢复脚本已
安装为 `samurai-platform 6-r2`；当前 `/usr/sbin/samurai-usb-recover`
SHA-256 是
`29859107008dde974997492466bb861dadc477b00e317edf4d1487fa3c97e548`。

`6-r2` 在 DWC3 unbind/bind 和标准模式服务重启完成后，再通过公开的
`/sys/class/udc/*/soft_connect` 做一次有界 disconnect/connect。这样
主机重新枚举时会重新执行 DHCP，而不是保留旧 NCM 适配器的失败状态。
它仍然只使用标准 UDC、DWC3 和 usb-moded 接口，没有增加私有传输层。

## 板级描述符

Developer 和 Tethering 使用：

```text
idVendor       0x0525
idProduct      0xa4a1
bDeviceClass   0xef
bDeviceSubClass 0x02
bDeviceProtocol 0x01
MaxPower       500
ncm qmult      20
manufacturer   Realme
product        SamuraiNCM
configuration  Samurai NCM / Samurai Tethering
```

MTP 使用 `0525:a4a2`，`bDeviceClass=0x00`。Mass Storage 的板级
`0525:a4a5` 描述符已配置，但本次没有把它当成已验收业务。

Developer 的地址是 `172.16.42.1/16`；标准 `unudhcpd` 服务参数为
`-i usb0 -s 172.16.42.1 -c 172.16.42.2`。Tethering 是
`10.42.0.1/24`，由 NetworkManager shared 连接启用 IPv4 forwarding。

## 实机结果

以下结果在 boot ID
`fc04a2e7-894b-4814-878e-6fdf5d44cc43` 上取得，内核 release
`7.3.1-rmx1931-samurai-v731-usbwake`。

### 普通重启后的默认路径

`samurai-platform 6-r1` 和 `usb-signaller 0.4.3-r3` 安装后执行普通
重启；随后在同一 boot 内升级到 `samurai-platform 6-r2`。启动完成后：

- `usb-signaller`、`usb-signaller-developer-mode`、`unudhcpd.usb0`、
  `samurai-usb-recover` 都是 started；
- 模式为 `developer_mode`，UDC `configured`，速度 `high-speed`；
- `Samurai NCM:usb0:activated`，`usb0=172.16.42.1/16`，carrier 1；
- Windows `USB\VID_0525&PID_A4A1\REALME-SAMURAI` 和
  `UsbNcm Host Device #5` 都是 Problem 0；
- Windows 标准 DHCP 地址为 `172.16.42.2/24`；
- 严格 host-key 的 NCM SSH 到 `172.16.42.1` 返回成功。

### Tethering

通过标准 D-Bus 执行 `set_mode("tethering_mode")` 后：

- gadget 为 `0525:a4a1`，class `0xef/0x02/0x01`，MaxPower 500，
  `qmult=20`；
- NetworkManager `Samurai Tethering` 激活，`usb0=10.42.0.1/24`；
- `/proc/sys/net/ipv4/ip_forward=1`；
- 随后切回 Developer 成功，地址恢复为 `172.16.42.1/16`。

### MTP

通过标准 D-Bus 执行 `set_mode("mtp_ffs_mode")` 后：

- gadget 为 `0525:a4a2`，class 0，MaxPower 500；
- `/dev/mtp/ep0` 到 `/dev/mtp/ep3` 出现，`umtprd` started；
- Windows `USB\VID_0525&PID_A4A2\REALME-SAMURAI` 为 WPD，Problem 0；
- 之后切回 Developer，NCM 连接恢复。

### Charging-only

通过标准 D-Bus 执行 `set_mode("charging_only")` 后：

- configfs 下没有绑定 UDC 的 gadget；
- UDC 为 `not attached`，`usb0` 不存在；
- `umtprd` 和 `unudhcpd.usb0` 停止；
- 切回 Developer 后重新建立 NCM。

### 有界 DWC3 恢复与主机 DHCP

在已建立 Developer NCM 链路时人为执行 `ip link set usb0 down`，
`samurai-usb-recover` 在 carrier 消失后触发：

```text
13:51:17 LINK_LOST state=configured carrier=
13:51:29 RECOVER_BEGIN attempt=1 reason=link_lost ...
13:51:36 RECOVER_OK attempt=1 reason=link_lost state=configured carrier=1
```

恢复后 boot ID 不变，UDC `configured`，`usb0` carrier 1，
NetworkManager `Samurai NCM` 重新激活。Windows 在同一恢复窗口内
重新取得 DHCP 租约：`172.16.42.2/24`，DHCP server
`172.16.42.1`，Lease Obtained `13:51:32`；`USB\VID_0525&PID_A4A1`
和 `UsbNcm Host Device #5` 仍为 Problem 0。恢复动作使用标准
`/sys/bus/platform/drivers/dwc3-qcom/{unbind,bind}` 和
`usb-signaller` 的 usb-moded D-Bus，最后用标准 UDC `soft_connect`
完成干净重枚举；最多两次尝试，稳定 300 秒后才重置预算。`rc-service`
调用有 30 秒上限，避免控制器异常时恢复服务永久卡在子进程等待。

升级到 `6-r2` 后又在同一 boot 重跑 Tethering、MTP、charging-only：
Tethering 的 Windows 客户端从 DHCP server `10.42.0.1` 取得
`10.42.0.157/24`；MTP 为 `0525:a4a2`、WPD Problem 0；切回
Developer 后 Windows 重新取得 `172.16.42.2/24`。charging-only 的
只读门禁原本错误地要求 UDC 必须为 `configured`，现已在
`check-usb-signaller-baseline.sh` 中按模式修正并实测通过。

### suspend 边界

一次 `rtcwake -m mem -s 15` 烟测返回 0，`suspend_stats.success`
从 0 增加到 1，boot ID 不变。日志显示 suspend entry/exit 的
`dmesg` 时差约 0.7 秒；该时差受本机 printk/RTC 时钟域影响，不能
单独作为“睡满 15 秒”的证明。恢复后短时间内 UDC 为
`not attached`、`usb0` DOWN；约 20 秒内自动恢复到 UDC
`configured`、carrier 1；该次 resume 后 NCM SSH 再次成功。Windows
UsbNcm 保持 Problem 0。早期一次恢复/重连测试中，Windows UsbNcm
曾停在 `169.254.x.x` APIPA；设备侧 `unudhcpd` 仍在监听 `:67`，
UDC/carrier/`usb0` 正常。该现象定位为主机没有重新发起 DHCP，而不是
gadget 失效；`6-r2` 的 UDC `soft_connect` 重枚举已在上述
`ip link down` 恢复中解决该路径。更长 suspend/resume soak 中的主机
DHCP 行为仍未验收。

因此当前结论是：

- **suspend 期间 NCM 不会保持为同一条活动链路**；DWC3 gadget 路径
  在 suspend 时 soft-disconnect，主机看到链路消失；
- **resume 后可以自动重连**，本次实测约 20 秒内恢复；
- 这不是同线 USB host-resume，也不是“PC 发一个包把手机唤醒”。

系统仍使用 postmarketOS 官方 `sleep-inhibitor` 的
`ssh-session-open`/`apk-running` 插件；`ssh-session-open` 依赖带
PTY 的交互式 SSH。BatchMode 自动化测试若要阻止 suspend，必须自己
持有标准 `elogind-inhibit --what=sleep --mode=block` 锁。

## 未验收

- 物理插线/拔线、Type-C 反插方向、不同线材和扩展 Hub；
- 一次真实的 USB 插拔唤醒（当前只验证了标准 Type-C 平台和
  s2idle 边界，不把 synthetic CC 事件当物理验收）；
- 长时间 resume 后 NCM 稳定性、重复 suspend/resume soak；
- Windows 物理 replug 后的 Code 43 是否仍出现；
- OTG host / USB3 / DP：当前内核没有 `DWC3_DUAL_ROLE` 和 xHCI；
- Mass Storage 业务、真实 MTP 文件传输和 Windows WPD 内容操作；
- `usb-signaller` 三个补丁已能按顺序无 fuzz 回放到 v0.4.3；
  上游提交前仍应做一次完整 `abuild` 和上游风格复核。

## 复现与回滚

只读检查：

```sh
dbus-send --system --type=method_call --print-reply \
  --dest=com.meego.usb_moded /com/meego/usb_moded \
  com.meego.usb_moded.mode_request
cat /sys/class/udc/a600000.usb/state
cat /sys/kernel/config/usb_gadget/usb-signaller-developer/UDC
nmcli -t -f NAME,DEVICE,STATE connection show
ip -br addr show usb0
```

恢复服务只读状态：

```sh
/usr/sbin/samurai-usb-recover status
```

回滚到旧 `samurai-usb` 只需显式停止 `usb-signaller` 并启动旧服务；
生产路径不应把旧服务重新加入 boot/default runlevel。不要恢复
GPIO10 extcon 或 `snps,gadget-keep-connect-sys-sleep`，也不要写
NV/persist/calibration/userdata。
