# SOFEF03F HBM 黑屏修复

状态：已刷入并完成真机验收（2026-11-10）。

## 根因

SOFEF03F 的亮度空间以 1023/1024 为界：

- `0..1023` 是普通亮度；
- `1024..2047` 是 HBM（高亮）模式。

原厂 `mipi_dsi_dcs_set_display_brightness()` 在 `brightness > 1023` 时
先写 `MIPI_DCS_WRITE_CONTROL_DISPLAY (0x53) = 0xe0` 进入 HBM，再写
`0x51` 亮度；离开 HBM 时先写亮度，再写 `0x53 = 0x20`。证据：

- 原厂 `drivers/gpu/drm/drm_mipi_dsi.c` 的 `VENDOR_EDIT` 分支
  （`realmeX2Pro-kernel-source`，本机快照
  `/home/cy122/work/realme-stock/drivers/gpu/drm/drm_mipi_dsi.c:1078`）；
- 原厂 `drivers/gpu/drm/msm/dsi-staging/dsi_panel.c:913` 调用该亮度
  接口；
- 本机原厂 DTS
  `dsi-panel-samsung-sofef03f-m-amoled-dsc-fhd-plus-90fps-cmd.dtsi`
  的 `qcom,mdss-dsi-bl-max-level = <2047>` 和
  `qcom,mdss-brightness-max-level = <2047>`。

主线面板驱动暴露了 `max_brightness=2047`，但旧实现只写 `0x51`，没有
HBM 切换。KWin/KScreen 在唤醒时把 50% 映射为 1024，恰好跨过边界，
面板物理黑屏；之后 KScreen 把亮度降到 308（30% 调光）又回到普通区间，
所以表现为“触摸/唤醒后黑屏，过一会又亮”。此前把 308 的恢复误判为
first-frame 时序修复生效。

## 为什么之前桌面没有触发

Phosh/Phoc 时期主要停留在内核默认 400 或 308 附近，没有 KScreen 的
`50% -> 1024` 恢复路径，因此没有跨过 1023/1024 边界。该 bug 是潜伏的
边界条件，不是 Plasma 引入的回归；Plasma Mobile 第一次稳定写入 1024
才把它暴露出来。即便其它桌面也使用标准 backlight class，只要 50% 被
映射到 1023 或更低，就不会触发。

## 电源键

实体电源键的官方路径是 elogind `HandlePowerKey=ignore` -> KWin
`DpmsInputEventFilter` -> PowerDevil `ToggleScreenOnOff`。此前 trace 已
确认按键能到 KWin，且完成 `drm_panel_backlight phase=0`、
`dpu_first_frame_backlight ret=0`、`phase=1`，但亮度是 1024，物理面板
仍黑。这个现象正是 HBM 边界 bug，因此可以解释“电源键看似没能亮屏”中
“DPMS 已唤醒但面板黑”的这一类。

它不能解释按键根本没到 KWin、DPMS 仍为 Off、或 suspend/resume 本身失败
的另一类问题。修复后仍应做一次实体电源键关/开验收；`kscreen-doctor
--dpms` 不能替代实体键。

## 标准层审计

- 使用 Linux 主线已有的 DRM panel、backlight class 和 MIPI DCS
  (`0x51`/`0x53`) API；没有新增私有 ioctl、sysfs、procfs 或服务。
- `0010` 静态检查只触及
  `drivers/gpu/drm/panel/panel-samsung-sofef03f.c`，新增行中没有
  `sysfs`/`ioctl`/`procfs`/`debugfs`/`of_property` 等私有或板级 ABI。
- 没有新增 DTB 属性或板级约束。1023/1024 和 HBM 序列是面板 DDIC 的
  硬件事实，放在 `panel-samsung-sofef03f.c` 是最薄的归属层。
- 当前补丁仍是本地内核补丁
  `linux-port/patches/v7.3.1/0010-...`（部署时使用等价的 0009），
  尚未进入 upstream Linux 或
  official pmaports 的 kernel APKBUILD。接口层面符合主线模型，交付
  层面还需要上游提交或在 pmaports 中带 provenance 地携带。
- `0010` 从 base tree 应用后与当前部署源码逐字节一致，因此本轮收敛
  不改变运行 Image，也不需要重新刷写；它只消除 0003/0005/0009 的脆弱
  叠加，方便后续复现和上游化。
- `kwin 0103-retry-transient-ebusy-commits.patch` 是独立的 downstream
  瞬时 EBUSY workaround，不是本次根因；Plasma 6.8.3 后应优先删除或替换
  为上游修复。
- `0003`/`0005` 的 first-frame 重发逻辑已被 `0009` 的工作队列逻辑覆盖
  大部分；后续可合并成单个面板补丁，减少补丁历史冗余。

## pmaports 携带方式

本机 pmaports 的 `device-realme-samurai` 明确使用
`device-realme-samurai-kernel-none`，注释写明“External EDK2/kernel
boot chain (no kernel installed by apk)”。因此当前没有可挂载
`0010` 的 pmaports kernel APKBUILD；v7.3.1 内核是外置源码树构建。

这条边界的正确做法是：

- 继续把 `0010-...-consolidated.patch` 作为外置 kernel patch set 的
  canonical 补丁，并用 `source-lock.json` 记录 provenance；
- 若要声称“official pmaports 携带”，必须先新增/接管一个 kernel
  APKBUILD，把 0010 放进 `source=` / `sha512sums`，而不是继续用
  `kernel-none`；
- 或者把 HBM quirk 提交到 upstream DRM panel，接受后删除本地补丁。

不要再把 0003/0005/0009 作为三个补丁叠加；0010 已对 base tree 验证
可逐字节复现部署源码。

## KWin 0103 评估

`0103-retry-transient-ebusy-commits.patch` 没有被删除。它处理的是
msm/DPU 对无 CRTC plane 的瞬时 `EBUSY`，与 HBM 黑屏是独立问题；当前
日志中它仍有独立的证据价值。删除条件应是 Plasma 6.8.3/上游已包含
对应修复，或一次不带 0103 的受控构建在 10 轮 DPMS/触摸中不再出现
`Atomic commit failed: EBUSY`。不能因为 HBM 修复生效就顺手删掉它。

2026-11-10 检查本地 `aports/main/kwin` 仍是 `pkgver=6.8.2`、`pkgrel=3`，
`Plasma/6.8.3` 分支当时不可取；因此本轮保留 0103，等上游稳定分支或
受控无 0103 回归再决定删除。
