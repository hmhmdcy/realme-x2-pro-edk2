# USB2 OTG / dual-role 适配状态（2026-11-12）

## 结论

目标已固定为：RMX1931 使用主线 Linux 的 DWC3 dual-role、xHCI、
PM8150B Type-C/TCPM 和标准 `usb-role-switch`，完成 USB2 OTG host
适配，并验证 U 盘、键盘、host/device 切换以及 NCM、MTP、充电和
suspend 回归。

本轮已完成真机部署并再次冷启动：OTG Image/DTB 冷启动、device-mode
NCM、Tethering、MTP、charging-only、15 秒 `s2idle` 和
synthetic `usb_role` host/device 切换通过。设备在 host role 下
实际注册了 xHCI USB2/USB3 root bus，切回 device 后 UDC/NCM 自动
恢复；本 boot 也完成了一次不依赖人工 DWC3 重绑的 host→device
往返和模式回归。

**尚未完成**：没有物理 Type-C OTG adapter/hub、U 盘、键盘、自动
PM8150B TCPM host 选择、反插方向或 VBUS source 验收。因此不能把
当前状态写成“OTG 外设已可用”。

### QSCRATCH VBUS override

OTG + `usb-role-switch` + 默认 peripheral 时，当前 v7.3.1 的
`dwc3-qcom` 在 probe 阶段不会执行角色 notifier，因此不会写入
QSCRATCH `VBUS_VALID` override，可能导致第一次 device 连接没有
session-valid。候选已加入上游通用修复：

`linux-port/patches/experiments/0011-usb-dwc3-qcom-vbus-override-probe.patch`

补丁 SHA-256：
`92c30eef2d440a226e31476a48a0a3e79984d88ae74c6d60d4914db05eee51df`。
它不是 RMX1931 板级 workaround，默认 peripheral 时在 probe 阶段
使能 override。`checkpatch.pl --strict` 为 0 errors / 0 warnings /
0 checks；真机 device 枚举已通过，host role 的 synthetic 切换也已
通过，但物理 OTG 外设和 VBUS source 仍未验收。

## 板级 DTB

源码：

`linux-port/dts/experiments/sm8150-samurai-usb-otg.dts`

该 wrapper 保持生产板的 `model`、`chassis-type` 和 USB 节点，只：

- 使能标准 PM8150B Type-C/TCPM；
- 使能 PM8150B USB VBUS regulator，限定为 5 V / 500 mA；
- 把 connector 描述为 `power-role=dual`、`data-role=dual`；
- 用标准 HS endpoint graph 连接 connector 与 DWC3；
- 把 DWC3 设为 `dr_mode=otg`、`usb-role-switch`，默认
  peripheral；
- 删除未装配的 SM8150 Ethernet 节点；
- 继续关闭 USB3 QMP/DP、第二 USB 控制器和 EUD。

没有 GPIO10 extcon、FSA4480/SBU mux、`keep-connect` 或私有
USB ioctl/传输层。RMX1931 的整机接口仍是 USB 2.0。

## postmarketOS USB 栈

`usb-signaller 0.4.3-r4` 已经识别本次部署产生的标准
`/sys/class/usb_role`：

- 向 `usb-moded` 的 `get_modes` 增加 `host_mode`；
- `mode_request` 在 host role 返回 `host_mode`；
- `set_mode("host_mode")` 切换 URS 并清理 configfs gadget。

真机 synthetic 结果：

- 写入 standard URS `role=host` 后，UDC 消失、xHCI 注册
  `usb1`/`usb2` 两个 root bus，`lsusb` 能看到两个 `1d6b` root hub；
- 写回 `role=device` 后，UDC、`usb0` carrier 和 Developer mode
  自动恢复；
- 最终 boot 连续 2 轮均如此，boot ID 不变，没有手工 DWC3 rebind；
  较早 boot 也完成过 3 轮。

仍未确认的是 PM8150B TCPM 在真实 Type-C OTG 设备/线缆下是否会
自动选择 host，以及 host side 外设枚举。若物理切换不能自动恢复，
应优先修标准 URS 事件到 usb-moded 的路径，而不是在板级脚本里
直接写 configfs。

`samurai-usb-recover` 在 `host_mode` 期间仍会 disarm；6-r3 新增
`mode_transition` 路径处理切回 Developer/Tethering 后 UDC
`configured` 但 host 没有拉起 carrier 的情况。实测
`19:59:07 MODE_REATTACH`、`19:59:17 RECOVER_BEGIN`、
`19:59:25 RECOVER_OK carrier=1`，Windows 在 `19:59:24` 取得
`172.16.42.2/24`，boot ID 不变。

## Boot guard

为允许无人值守部署，rootfs 增加了 one-shot `samurai-boot-guard`：

- 只有 rootfs 写入 `armed` 标记后才工作；
- 下一 boot 若 600 秒内没有通过 SSH 执行 `confirm`，就把事先校验
  的 boot/logdump 回滚镜像写回并重启；
- 回滚镜像大小、SHA-256、分区可写和未挂载状态均在启动和写入前
  复查；
- 本次回滚目标是部署前 boot `69cf8066...` / logdump
  `767b7985...`；
- 两次 smoke/正式部署都在恢复 SSH 后 confirm，marker 已清除，
  `samurai-boot-guard` 当前 idle；
- 超时回滚的写回顺序已改为先 `logdump`、后 `boot`，使最后一个
  关键启动镜像写入成功后仍保持成对一致；
- guard 仅作为 `linux-port/diagnostics/` 的无人值守运维工具安装，
  尚未并入 `samurai-platform` APKBUILD；普通生产运行不依赖它；
- `test-samurai-boot-guard.sh` 用临时文件验证 60 秒超时后的
  `logdump→boot` 写回顺序，不接触真实块设备或重启主机。
