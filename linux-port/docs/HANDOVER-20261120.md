### 3. 5 GHz still not fully well

| band | ch | loss | min/avg/max |
| --- | --- | --- | --- |
| 2.4 GHz | 11 | 0 % | 0.9 / **4.9** / 35.7 ms |
| 5 GHz | 36 | 0 % | 1.0 / **257-440** / 1371 ms |

5 GHz was 884-1140 ms earlier in the session and settled at 257-440 ms over
five consecutive 30-packet runs (150 packets, zero loss, `beacon loss 0`).
Same AP, same phone, same boot. 2.4 GHz is perfect, so this is not a general
protocol-stack problem. Remaining gap is the long tail (min 1 ms vs max 1.4 s),
which points at the AP's own 5 GHz side (the Windows AX210 cannot see that
AP's 5 GHz BSS at all) or ath10k 5 GHz aggregation/scheduling. Next step needs
no code change: retest against a different 5 GHz AP.

## Open items, in priority order

1. **`taint=512` on the new kernel.** Two `dsi0_phy_pll_out_dsiclk`
   `already disabled/unprepared` WARNs from the generic clk reparent path.
   Root cause and a minimal upstream-style fix are written up in
   [WIFI-BAND-LATENCY-20261120](WIFI-BAND-LATENCY-20261120.md) §10.6; it was
   deliberately not patched privately. Display/backlight/DPMS all work.
2. **NCM device→host direction is dead on the host side.** Phone side is
   healthy (`udc=configured`, gadget `usb-signaller-developer` bound to
   `a600000.usb`, NCM function present, `usb0` has `169.254.42.1` +
   `172.16.42.1`, sshd listening). The failure is one-directional:

   | measurement | value |
   | --- | --- |
   | phone `usb0` RX packets | 18,k+ (host→device packets arrive) |
   | phone `usb0` TX packets | stuck at 55 → 111 (frames not completing) |
   | phone qdisc `Sent` | 610 pkt, dropped 0, requeues 2 |
   | host `以太网 10` ReceivedBytes | frozen at 996 → 1111 |
   | host `以太网 10` ReceivedUnicastPackets | 0 |

   So the device hands frames to the URB layer but the host NCM driver never
   harvests them. `qmult=20` (40 in-flight requests) is exactly the state you
   expect when the host stops re-arming bulk-IN. Rebinding the gadget, re-issuing
   `mode_request`, and writing `UDC` again all fail to recover it; the host-side
   adapter statistics stay frozen. This needs a **physical USB re-plug** (or a
   host reboot) to reset the host NCM driver.

   Explicitly **not** the cause: the host `codex_sandbox_offline_block_*`
   firewall rules. They are Any/Any/Block, but Wi-Fi SSH, the router probe on
   port 80 and other hosts all connect normally, and the phone still receives
   the host's packets — the loss is only device→host.
3. **Camera.** `media0` + 8 `msm_vfe*_video` nodes exist and all four sensors
   are bound (`7-0010`, `9-0010`, `8-002d`, `6-0010`).  Inspected with the
   v4l-utils `media-ctl` binary taken from `/root/v4u` (read-only):

   ```text
   msm_csiphy0..3   2 pads, 2 links each   (source -> msm_csid0/1)  OK
   msm_csid0        5 pads, 12 links                               OK
   imx471 9-0010    1 pad, 0 link
   s5kgw1 6-0010    1 pad, 0 link
   imx319 7-0010    1 pad, 0 link
   s5k3m5 8-002d    1 pad, 0 link
   ```

   Every internal CAMSS link exists; the missing layer is exactly
   `sensor -> csiphy`, i.e. `media_create_pad_link()` in
   `camss_subdev_notifier_complete()` never ran.  DT side was re-checked and
   is complete: `port@0` (s5kgw1), `port@1` (imx319), `port@2` (imx471),
   `port@3` (s5k3m5) all exist with `remote-endpoint` back-references, so this
   is a notifier completion problem, not a missing-port problem.  Debugging it
   further needs kernel-side instrumentation (dynamic debug / a temporary
   print in `camss_parse_ports`), i.e. another kernel build+flash.
   Note: `/dev/v4l-subdev*` being empty is **normal** for qcom-camss (one
   platform device, internal graph) — do not treat that count as a defect.
4. **`/lib/firmware/ath10k/WCN3990/` still unowned** by any package.
5. Nothing committed or pushed (repo has unrelated pre-existing dirty files
