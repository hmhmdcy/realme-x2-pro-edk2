# Wi-Fi KCM radio-control loop (2026-11-13)

## Symptom

Turning Wi-Fi off and then on in the Plasma Mobile settings UI left
`phy0` soft-blocked and `wlan0` DOWN. NetworkManager itself was
healthy: `nmcli radio wifi off` / `on` recovered normally, ath10k
scanning and DHCP worked, and USB NCM SSH stayed connected.

## Layered diagnosis

The failure belongs to the desktop UI layer, not to the board or the
wireless driver:

| Layer | Observation | Conclusion |
| --- | --- | --- |
| SM8150 / ath10k | driver loaded, `rfkill` hard block clear, scan and DHCP work after radio restore | no kernel or firmware workaround |
| NetworkManager / wpa_supplicant | plain `nmcli radio wifi off/on` succeeds | no service-policy change, no NetworkManager restart |
| rfkill | `phy0` ends soft-blocked only while the KCM is stuck | rfkill is a victim of repeated radio writes |
| Plasma Mobile UI | `plasma-settings -m kcm_mobile_wifi` writes `wireless-enabled:on/off` many times per second | root cause is in the mobile Wi-Fi KCM |
| samurai board | no phone-specific Wi-Fi state is involved | no board patch; recovery script is emergency-only |

## Root cause

`plasma-nm` 6.8.2, the current `master` branch, and the `Plasma/6.8`
branch contain this block in `kcms/kcm_wifi_mobile/ui/main.qml`:

```qml
FormCard.FormSwitchDelegate {
    id: wifiSwitch
    text: i18n("Wi-Fi")
    checked: enabledConnections.wirelessEnabled
    onCheckedChanged: {
        handler.enableWireless(checked);
        checked = Qt.binding(() => enabledConnections.wirelessEnabled);
    }
}
```

`onCheckedChanged` is not a user-action signal. It also runs when
`EnabledConnections` follows a NetworkManager or rfkill update.
`FormSwitchDelegate` itself writes the inherited `checked` property
when its inner switch is toggled, so the handler can observe both the
user toggle and the resulting radio-state notification. The explicit
`Qt.binding()` then re-evaluates `checked` before the previous
`NetworkManager::setWirelessEnabled()` call has necessarily taken
effect. The two writes can alternate, producing the observed
`radio-control wireless-enabled:on/off` feedback loop.

The desktop network applet in the same plasma-nm tree already uses
the correct pattern:

```qml
onToggled: handler.enableWireless(checked)
```

`FormSwitchDelegate` forwards `toggled` only for the user action from
its inner switch. A programmatic change of the bound `checked`
property does not emit it.

Upstream has a matching open merge request,
[!695](https://invent.kde.org/plasma/plasma-nm/-/merge_requests/695)
("kcm_wifi_mobile: Fix disabling Wi-Fi causing an infinite loop",
authored 2026-11-10). It targets `master`, has not been merged, and
is not present in a released plasma-nm. The MR changes only the
signal name and keeps the explicit `Qt.binding()`; the local patch
also removes that redundant rebinding. On the device harness the MR
variant settled correctly but changed `checked` false/true/false after
one toggle; the local variant produced one transition.

## Fix

Patch `linux-port/packages/plasma-nm/0001-kcm-mobile-wifi-use-onToggled.patch`
changes the mobile KCM to:

```qml
checked: enabledConnections.wirelessEnabled
onToggled: handler.enableWireless(checked)
```

The declarative binding stays in place, so the switch continues to
follow quick-settings, `nmcli`, and rfkill changes. No manual
`Qt.binding()` reassignment is needed.

## Signal-level verification on the RMX1931

A standalone QML harness used the real `PlasmaNM.Handler`,
`PlasmaNM.EnabledConnections`, and
`FormCard.FormSwitchDelegate` objects. It did not use the KCM binary.

Old handler, one user-like toggle:

```text
OLD changed true  count 1
OLD changed false count 2
OLD changed true  count 3
OLD changed false count 4
OLD changed true  count 5
OLD changed false count 6
P1 NM false sw false changes 6
P2 programmatic NM on
P3 NM false sw false changes 14
POST: nmcli radio wifi disabled
POST: phy0 Soft blocked: yes
```

The loop continued after the programmatic "on" request and left the
radio blocked. Fixed handler, same sequence:

```text
STATE checked true
P0 NM true sw true
STATE checked false
USER TOGGLE false
P1 NM false sw false
P2 programmatic NM on
STATE checked true
P3 NM true sw true
POST: nmcli radio wifi enabled
POST: phy0 Soft blocked: no
```

This isolates the bug to the KCM handler: the NetworkManager and
rfkill stacks behaved correctly when driven once.

The raw QML harnesses and output logs are in
`E:/edk2-samurai-out/standard-arm64-v731/wifi-kcm-20261113/`.

Rollback:

```sh
cp -p /root/kcm_mobile_wifi.so.orig-20261113 \
  /usr/lib/qt6/plugins/plasma/kcms/systemsettings/kcm_mobile_wifi.so
```

Do not restart NetworkManager during rollback while USB NCM is the
only remote path; killing the stuck KCM or using
`/usr/sbin/samurai-wifi-recover` is sufficient for the radio loop.

## Standardization disposition

- Kernel/DTB: describe ath10k and rfkill wiring only; no change.
- Network service: NetworkManager remains the owner of radio state;
  no board policy.
- Desktop/UI: fix plasma-nm `kcm_wifi_mobile`; this is a general
  Plasma Mobile bug, not a samurai bug.
- Distribution: carry the patch as a temporary Alpine aports
  `plasma-nm` package revision until upstream releases a fixed
  version, then remove the local package.
- Board: keep `samurai-wifi-recover` only as an emergency backend
  for an already-stuck UI process. It must not be the primary fix.
