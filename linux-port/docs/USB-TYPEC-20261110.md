# USB2 Type-C 标准平台适配（2026-11-10）

## 目标边界

本层只把 RMX1931 的 USB-C CC/PD、数据角色和 DWC3 连接关系交给 Linux
主线已有的 PMIC Type-C/TCPM、USB role switch 和标准 OF graph，并分成
“DTB-only sink”“DWC3 双角色内核”“USB3/DP”三个可独立回滚的阶段。
它不是“打开 USB3/DP”或“让手机给外设供电”的合并改动。

分层如下：

| 层 | 责任 | 本板实现 |
| --- | --- | --- |
| L1 硬件事实 | 线序、供电、GPIO、模拟开关 | 只来自 RMX1931 stock DTB/DTBO 和真机观测 |
| L2 板级 DT | PM8150B Type-C、PD PHY 电源、DWC3 HS endpoint | DTB-only overlay，可单独回滚 |
| L3 内核模型 | `qcom,pm8150b-typec`、TCPM、`usb-role-switch`、DWC3/xHCI | sink 使用现有 gadget-only 配置；dual 需另建 `DWC3_DUAL_ROLE+xHCI` Image |
| L4 UAPI | `/sys/class/typec`、`/sys/class/usb_role`、UDC | 不新增私有 ioctl/sysfs |
| L5 服务 | NCM/configfs、DHCP、SSH、sleep-inhibitor | 保持 postmarketOS/KDE 现有边界 |

## RMX1931 硬件结论

- stock DTS 的 `usb0` 使用 `dr_mode = "otg"`，但把
  `maximum-speed` 限制为 `high-speed`；产品化主线继续遵守这个限制。
- 当前生产内核实际是 `CONFIG_USB_DWC3_GADGET=y`，未启用
  `CONFIG_USB_DWC3_DUAL_ROLE`，且 `CONFIG_USB_XHCI_HCD` 未编译。
  因此只把 `dr_mode` 改成 OTG 不会得到 host，必须另行构建双角色 Image。
- stock `usb0` 的 extcon 是 PM8150B PD PHY 和 EUD；PM8150B
  Type-C/SMB5/PD PHY 节点存在。
- stock DTS 没有 FSA4480 I2C 节点；配套音频 DTS 还明确写着
  “not use fsa4480”。不要把 OnePlus `hotdog` 的 FSA4480/SBU mux
  当成 RMX1931 硬件。
- stock DP 驱动使用 GPIO43/51/38（AUX EN/AUX SEL/USB plug CC）和
  GPIO100（`fsa_usbc_ana_en`）作为板级模拟路径。它们是未来 USB3/DP
  独立层的证据，不应混入 USB2 NCM 基线。

## 两个独立候选

### 1. `usb2-typec-sink`：首先验证

文件：
[`usb2-typec-sink.dtso`](../dts/experiments/usb2-typec-sink.dtso)

- `pm8150b_typec` 启用，PD PHY 使用 `vreg_l2a_3p1`；
- connector 固定 `power-role = "sink"`、`data-role = "device"`；
- `pm8150b_vbus` 只注册为 500 mA 限流的供应器，TCPM 在 sink 配置下
  不应使能它；
- DWC3 保持现有 `dr_mode = "peripheral"`，不添加 `usb-role-switch` 或
  HS graph；这一层只增加 PM8150B TCPM，数据路径不变；
- 只保留 HS PHY，QMP/USB3/DP 继续 disabled；
- 不加 FSA4480/SBU graph。

此层要回答的是：启用 TCPM 后 NCM/SSH 是否仍稳定、CC 正反插是否被
正确识别、长时间空闲/挂起是否出现新的 probe/IRQ 问题。它不验证 host
模式，也不验证 VBUS 输出能力。

### 2. `usb2-typec-dual`：第一层通过后再测

文件：
[`usb2-typec-dual.dtso`](../dts/experiments/usb2-typec-dual.dtso)

- connector 改为 `power-role = "dual"`、`data-role = "dual"`；
- 首选角色仍是 sink，source 能力先收紧到 5 V / 500 mA；
- 仍然只有 USB2 HS，不打开 QMP/DP；
- 必须配套 `CONFIG_USB_DWC3_DUAL_ROLE=y`、`CONFIG_USB_XHCI_HCD=y`、
  `CONFIG_USB_XHCI_PLATFORM=y` 的新 Image；当前生产 Image 不能跑本层；
- 第一次 host 测试必须使用有源 USB-C dock，确认 VBUS/电流和角色切换
  安全后，再试无源 U 盘。

这一层不是默认部署值。它需要单独记录 PM8150B VBUS、充电器与板级
保护链的实际行为。

## USB 插拔唤醒：独立的第三层

> **2026-11-11 撤回**：本节描述的 `usb2-vbus-wake` 已被真机否定并删除。
> 厂商 DTS 注释掉了 GPIO10 `vbus-gpio` 和 `&usb1` 消费者；实测 GPIO10
> 不跟随 VBUS、IRQ 120 始终为 0。该 GPIO 路径已由标准 PM8150B
> Type-C/TCPM 取代。见
> [USB-REMOTE-WAKE-20261111](USB-REMOTE-WAKE-20261111.md) 和
> [USB-TYPEC-WAKE-20261112](USB-TYPEC-WAKE-20261112.md)。

> **2026-11-12 状态**：标准 PM8150B Type-C/TCPM、`usb-c-connector`、
> PM8150B VBUS regulator 和 Type-C `wakeup-source` 已作为持久
> DTB/Image 部署；3 轮 15 秒 + 1 轮 60 秒以及追加 8 轮 15 秒
> `s2idle` 通过，UDC/NCM 自动恢复，Windows PnP Problem Code 0。
> suspend 边界 diagnostic 已证明 Type-C IRQ → SPMI → PDC，但它不是
> 电缆事件；物理插线/拔线唤醒仍需真实动作，不能写成已通过。详见
> [`USB-TYPEC-WAKE-20261112.md`](USB-TYPEC-WAKE-20261112.md)。

Type-C sink/dual 与 USB suspend wake 不能合并验收。当前已另外构建
DTB-only `usb2-vbus-wake`：

- 事实来源是 Android 真机运行 DT 的 `extcon_usb1`，它绑定到 PM8150
  GPIO10 的 VBUS 检测输入；
- 使用主线 `linux,extcon-usb-gpio`；extcon binding 没有
  `wakeup-source` 属性，驱动也不读取它，因此该属性已删除。唤醒启用
  由标准 udev `power/wakeup` 策略负责；
- 将 SPMI PMIC arbiter 的 periph IRQ 从裸 GIC SPI 改到 PDC pin 1
  （PDC range 映射到 GIC SPI 481），使子 GPIO 的 wake 请求真正进入
  Qualcomm PDC；
- rootfs 只增加一条 udev 策略，把对应平台设备的 `power/wakeup`
  设为 enabled；不增加常驻服务，不改 postmarketOS `sleep-inhibitor`；
- DWC3 数据路径保持 `dr_mode=peripheral`，不打开 host/OTG。

候选 DTB SHA-256：

```text
ea4ba7bc55eae8d63c8b7c7277634b1d016c278d23753fb04d98040692ebf887
```

该层只保证“插拔 USB 线/充电器可以成为唤醒源”，不保证同一根线的
NCM 在 suspend 期间保持在线。DWC3 在系统 suspend 仍会 soft-disconnect；
主机发数据包、magic packet 或 SSH SYN 都不是手机唤醒源。主机主动
USB resume 需要另做通用 DWC3 peripheral suspend/wake 补丁。

构建、真机门禁、回滚和官方 postmarketOS 休眠边界见
[`USB-WAKE-20261110.md`](USB-WAKE-20261110.md)。

## 当前内核配置缺口

当前生产配置是：

```text
CONFIG_USB_DWC3_GADGET=y
# CONFIG_USB_DWC3_DUAL_ROLE is not set
# CONFIG_USB_XHCI_HCD is not set
```

所以过去“NCM 能用”只证明 gadget 路径完整，不能证明 OTG/role-switch
或 host 已接入。dual-role 候选的 Kconfig fragment 在
[`usb2-typec-dual.fragment`](../configs/v7.3.1/usb2-typec-dual.fragment)。
当前 `REGULATOR_QCOM_USB_VBUS=m`，所以默认 Image 上的 TCM 可能先
probe-defer，等标准 udev/modprobe 加载 `qcom_usb_vbus-regulator.ko`
后再完成绑定；这不等于 USB NCM 故障，门禁需要同时检查模块和
`/sys/class/typec`。独立 dual 配置把它改为 built-in，避免该延迟。

同时删除了 `USB_DWC3_SAMURAI_APSD_OWNER` /
`USB_DWC3_SAMURAI_APSD_PD5V_CLIENT` /
`USB_DWC3_SAMURAI_APSD_EUD_OFF_CLIENT` 三个未启用、引用不存在源文件的
私有 Kconfig/Makefile 钩子。它们既不可编译，也不是标准 USB 模型：
[`0005-usb-dwc3-qcom-remove-unused-samurai-apsd-kconfig.patch`](../patches/v7.3.1/0005-usb-dwc3-qcom-remove-unused-samurai-apsd-kconfig.patch)。

## 上游与同类机型依据

- 主线 SM8150 HDK 使用同一套 PM8150B Type-C、DWC3 role-switch 和
  connector graph：
  [`sm8150-hdk.dts`](https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/qcom/sm8150-hdk.dts)
- OnePlus 7T Pro `hotdog` 已真机验证 USB2 role switch；其补丁保留了
  `maximum-speed = "high-speed"`，并把 USB3/DP 放在后续独立补丁：
  [`hotdog-linux-bringup`](https://github.com/Sr-0w/hotdog-linux-bringup)
- Xiaomi Pad 5 `nabu` 是更接近“只做 USB2 Type-C”的 SM8150 参考：
  [`sm8150-mainline`](https://github.com/map220v/sm8150-mainline)
- Realme X3 的 postmarketOS 端口是更接近本项目品牌/SoC 的参考；其
  README 只声明 USB Gadget，并明确 Suspend/Resume 仍坏，提醒我们不能把
  “有 dual-role DTS”误当成 host 或唤醒已验收：
  [`pmos_realme_x3`](https://github.com/sm8150-linux-mainline/pmos_realme_x3)
- 主线 PM8150B Type-C/TCPM 驱动和 binding：
  [`qcom_pmic_typec.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/usb/typec/tcpm/qcom/qcom_pmic_typec.c)、
  [`qcom,pmic-typec.yaml`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/Documentation/devicetree/bindings/usb/qcom,pmic-typec.yaml)
- Qualcomm 2026-10 的 `dwc3-qcom` 系列还包含一个通用修复：OTG +
  `usb-role-switch` 且默认 peripheral 时，应在 probe 阶段设置
  QSCRATCH `VBUS_VALID` override。当前 v7.3.1 没有该修复；如果首轮
  UDC 枚举需要额外一次角色切换，应优先评估这个通用补丁，而不是加板级
  workaround：
  [`PATCH v4 7/7`](https://lists.openwall.net/linux-kernel/2026/11/02/438)

## 构建与验证

构建两套 DTB-only 候选：

```sh
python3 linux-port/scripts/build-usb-typec-candidates.py \
  --kernel-root /home/cy122/standard-arm64-v7.3.1 \
  --build-root /home/cy122/samurai-v731-build \
  --output-dir /mnt/e/edk2-samurai-out/standard-arm64-v731/usb-typec-20261110 \
  --profile all
```

产物只包含合并后的 DTB、overlay、manifest 和哈希；脚本不修改 Image、
boot 分区、NV、persist、calibration 或 userdata。

解析但暂不构建 dual-role 内核配置：

```sh
linux-port/scripts/prepare-usb-typec-dual-config.sh
```

该脚本使用独立 `O=` 目录和 `ARCH=arm64`，只运行 `olddefconfig`，不改
当前生产 `.config`。差分应只包含 DWC3 gadget→dual-role、xHCI 和
`REGULATOR_QCOM_USB_VBUS=m→y`；不会把整理前的私有 APSD Kconfig 再带回。

本轮离线候选：

| 候选 | DTB SHA-256 | 当前内核配置 |
| --- | --- | --- |
| sink | `b18da562...657bd792` | 满足，数据路径保持 peripheral |
| dual | `ef8e40ba...7e87e58d` | 缺 DUAL_ROLE 和 xHCI，需新 Image |

候选 manifest 为
`E:/edk2-samurai-out/standard-arm64-v731/usb-typec-20261110/manifest.json`；
其中同时记录 base DTB、overlay、DTB、配置差分和命令回执。

设备端只读门禁：

```sh
sh linux-port/scripts/check-usb-typec-baseline.sh
sh linux-port/scripts/check-usb-typec-baseline.sh --require-configured
```

建议顺序：

1. 备份当前 kernel FAT 的 `/Image`、`/samurai.dtb` 与 boot 回读；
2. 只替换 `/samurai.dtb` 为 sink 候选，Image 保持同源已验证版本；
3. 普通重启，确认 UDC/NCM/SSH；
4. 正反插各一次，记录 `/sys/class/typec/*` 和 UDC；
5. 跑 NCM 大传输/心跳矩阵，确认 CAMSS 等无关硬件不回归；
6. sink 通过后，先用 `prepare-usb-typec-dual-config.sh` 的配置构建
   独立 Image/modules，再测试 dual-role 候选和 500 mA source；
7. USB3/DP 作为第三层，单独处理 QMP、DP altmode 和 AUX/USB-C 模拟
   开关，不与本层合并。

## 当前禁止项

- 不把 `usb2-typec-dual` 当作正式默认；
- 不打开 QMP/USB3/DP；
- 不添加未经 RMX1931 证据支持的 FSA4480；
- 不把 `usb-psy-name` 这类测试属性写成正式设计；
- 不用 OOT 模块替代主线 TCPM/DWC3；
- 不在没有回滚电源键/RTC 恢复手段时测试 suspend 后 USB wake。
