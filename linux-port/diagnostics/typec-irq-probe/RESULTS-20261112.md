# PM8150B Type-C IRQ probe results (2026-11-12)

This module is diagnostic-only.  It was not added to boot, DTB, the
`samurai-platform` package, or any production service.

## Awake register cycle

The module borrowed the parent SPMI regmap and wrote
`TYPEC_DISABLE_CMD` (`0x01`) to `TYPEC_MODE_CFG_REG` (`0x44`), waited
1.5 seconds, and restored `EN_SNK_ONLY` (`0x02`).

Observed on the device:

```text
cc-state-change IRQ      2 -> 4
attach-detach IRQ        2 -> 4
sig-tx IRQ               2 -> 4
UDC                      configured -> configured
boot_id                  unchanged
```

The dmesg log contains a `hard-reset` / `isr: tx_sig` pair around each
mode transition.  This proves the register path and Type-C IRQ delivery,
not a cable-driven wake.

## Suspended synthetic event attempt: failed

The module's PM notifier armed a kthread and requested a mode cycle eight
seconds after `PM_SUSPEND_PREPARE`.  With a 30-second RTC safety alarm,
the kernel slept for the full alarm and no Type-C IRQ delta was seen
during the sleep.  The kthread's `msleep()` timer is frozen with the
s2idle timekeeping domain, so it did not run at the intended time.

Result: `FAIL` for a synthetic wake.  This method must not be used as a
substitute for a physical cable event.  A later hardware-generated
PMIC event, or a real insertion/removal, is still required.

## Suspended boundary-generated event: PASS

`typec_wake_near.ko` is a second, diagnostic-only module.  It creates a
dummy platform device as a device-link supplier for the PM8150B Type-C
device.  Its `suspend_late` callback therefore runs after the Type-C
driver has armed its wake IRQs, but before the final `s2idle` transition.
It writes `TYPEC_DISABLE_CMD` to `TYPEC_MODE_CFG_REG` (`0x44`) and
restores the original mode on resume.  This produces a real PMIC CC state
change while the system is suspended; it is not a cable emulator.

Two armed runs and two controls were recorded with a 15-second RTC safety
alarm:

| Case | RTC elapsed | suspend success | Type-C IRQ delta | TCPM wake events |
| --- | ---: | --- | ---: | --- |
| armed | 5 s | +1 | +4 | not sampled |
| armed repeat | 5 s | +1 | +4 | not sampled |
| armed, TCPM sampled | 4 s | +1 | +4 | 76 -> 85 (+9) |
| unarmed control | 20 s | +1 | 0 | 76 -> 76 |

The armed runs returned well before the RTC alarm, kept the same
`boot_id`, incremented `suspend_stats/success`, and incremented the
PM8150B `cc-state-change` and `attach-detach` IRQs.  UDC remained
`configured` and `usb0 carrier=1` after resume.  The unarmed control
slept through the full RTC interval with no Type-C IRQ delta.

A separate `power/wakeup=disabled` control likewise slept through the
full interval; no boundary-generated wake was observed.  This confirms
that the early return depends on the Type-C wake source being armed.

This is a positive test of the Type-C IRQ -> SPMI -> PDC s2idle wake
path.  It is **not** a physical cable insertion/removal test and does
not prove host-side VBUS wake or same-cable U3 host-resume.  The module
was unloaded after the test.  It is diagnostic-only and must not be
shipped or added to the boot image, DTB, or `samurai-platform` package.

## Eight-cycle suspend/NCM soak

After the boundary-wake test, the diagnostic module was unloaded and an
eight-cycle `rtcwake` soak was run with the production Type-C DTB and
kernel.  Each cycle used a 15-second RTC alarm:

| Cycles | RTC elapsed | suspend success | UDC/carrier after recovery |
| ---: | ---: | --- | --- |
| 8/8 | 17 s each | 18 -> 26, +8 | configured / 1 every cycle |

All cycles slept for the full RTC interval, kept the same `boot_id`, and
left Windows PnP Problem Code 0.  The host re-enumerated after each
resume; UDC was briefly `not attached`, then returned to `configured`
and carrier 1.  There were eight `LINK_LOST` records in the recovery
service log but no `RECOVER_BEGIN`: the host's own re-enumeration
recovered the gadget before the bounded 12-second rebind watchdog fired.
No forced DWC3 unbind/bind was needed.

The soak logs are in
`usb-typec-wake-probe-20261112/soak-8x15-20261112/`; the summary file
SHA-256 is
`bf1346621b4e241e5ba060b401a4b70917b095d1c21d72b1f84eec6810d62c4e`.
The first and last cycle logs have SHA-256
`f4a4137e183608875a5ab499f301e32a25a464ae94cb6be09769fb7e27733edb`
and
`102a9bf5ca8a714b8e5a9490414a5f4162c165f1cb9c1bc64c790a827e718d37`.

This still does not exercise a physical cable removal or insertion.

## Observer survival check

A final 15-second `rtcwake` cycle ran while
`typec-transition-observer.sh` was active.  RTC elapsed time was 17
seconds, `suspend_success` went 26 -> 27, `boot_id` stayed unchanged,
and the observer process was still alive after resume.  Its log
captured UDC `configured -> not attached -> configured` and carrier
`1 -> 0 -> 1`; the normal high-speed NCM link was restored within about
one second.

The observer is diagnostic userspace only.  It records state changes
for later physical-cable correlation but cannot identify the wake
source.

## Physical wake-script negative control

`test-usb-typec-wake.sh remove 10` was run deliberately without
unplugging the cable.  The script printed its 8-second countdown,
suspended, woke from the 10-second RTC alarm after 12 seconds, and
correctly reported `RESULT: FAIL`:

```text
suspend success     27 -> 28
boot_id             unchanged
online              1 -> 1
Type-C IRQ delta    0
TCPM events         87 -> 87
pm_wakeup_irq       empty
Windows PnP         Problem Code 0
```

This is the required no-false-positive control for the test script: an
RTC-only wake with no cable transition cannot produce `RESULT: PASS`.
The default log path also worked:

```text
/var/log/samurai/typec-wake-negative-control-20261112.log
```

## Recovery service integration

The `samurai-platform` recovery service was separately tested:

- a real `dwc3-qcom` unbind was recovered automatically after the
  12-second link-loss grace;
- the fake-sysfs state-machine test exercised
  `VBUS_ON seen=1 -> RECOVER_BEGIN reason=reattach -> RECOVER_OK`;
- UDC returned to `configured`, `usb0 carrier=1`, and the service
  stopped after its bounded attempt.

The signed `samurai-platform 5-r30` APK was built and installed; the
module was unloaded afterward.  Physical Type-C insertion/removal and
the same-cable U3 host-resume remain unverified.
